# 交易方字段配置解释规则

本文件是 `contract-cli mdm fields list --biz-line vendor` 返回结果用于交易方创建、PATCH 时的统一解释口径。字段配置描述“某个模块内的字段规则”，不能直接推导为“创建时必须提交所有模块”。

## 模块语义

| module | 业务对象 | 创建时是否必须提交 | `required` 的含义 |
| --- | --- | --- | --- |
| module 0 | 交易方基础信息 | 主对象始终存在 | 当前租户启用的必填字段属于全局必填，创建前只询问仍缺失的字段 |
| module 1 | 经营地址 `vendorAddresses` | 子项集合本身可选 | 仅在提交该子项时生效；每条地址分别满足其内部必填字段 |
| module 2 | 联系人 `vendorContacts` | 子项集合本身可选 | 仅在提交该子项时生效；每条联系人分别满足其内部必填字段 |
| module 3 | 银行账户 `vendorAccounts` | 子项集合本身可选 | 仅在提交该子项时生效；每条账户分别满足其内部必填字段 |
| module 4 | 公司视图 `vendorCompanyViews` | 子项集合本身可选 | 仅在提交该子项时生效；每条公司视图分别满足其内部必填字段 |
| module 5 | 智书合同签约信息 | 不属于 MDM 交易方维护 | 不进入交易方创建请求或 PATCH 请求，不向用户索取 |

## Agent 决策规则

1. 最小创建只收集 module 0 中当前租户要求、且用户尚未提供的全局必填字段。
2. 用户没有要求地址、联系人、银行账户或公司视图时，不得据其内部 `required` 标记要求用户补充该模块。
3. 用户明确要求提交 module 1～4 的某类子项时，再逐条检查该子项内部的必填字段；一类子项的规则不能扩散到其他模块。
4. module 5 即使出现在字段配置响应中，也不进入交易方创建请求，不得转化为创建参数。
5. 字段值只能来自用户明确提供的信息或用户对候选值的确认。不得猜测或推荐默认值，不得虚构国家、交易方性质、地址、联系人、账户或公司代码。
6. 缺少全局必填字段时，一次只询问实际缺少的字段；枚举字段展示合法选项供用户选择，不替用户作业务决定。
7. PATCH 只提交用户要求修改的字段。字段配置中的其他必填字段不代表 PATCH body 必须重复提交；最终快照由服务端校验。

## 自定义字段值属性

主对象以及经营地址、联系人、银行账户、公司视图中的 `extendInfo` 使用同一套映射：

| fieldType | 字段类型 | 唯一值属性 | 值格式 |
| --- | --- | --- | --- |
| 0、1 | 单行文本、多行文本 | `fieldValue` | 字符串 |
| 2 | 数字 | `num` | JSON 数字，`0` 是有效值 |
| 3、5 | 单选、下拉单选 | `fieldValue` | 字段配置返回的合法选项值 |
| 4、6 | 多选、下拉多选 | `options` | 字段配置返回的合法选项值数组 |
| 7 | 日期 | `date` | `yyyy-MM-dd` |
| 8 | 日期范围 | `rangeDate` | 按开始、结束顺序传两个 `yyyy-MM-dd` 字符串 |
| 12 | 附件 | `appendix` | 已有附件的 `{ "fileId": "..." }` 数组 |
| 14 | 人员 | `employee` | 人员 ID 数组；单选或多选以字段配置为准 |

每个自定义字段只提交与 fieldType 对应的一个值属性，不得同时提交冲突属性。`fieldCode` 必须来自字段配置；`fieldType` 可以省略并由服务端按配置识别，显式传入时必须与配置一致。选项值必须来自字段配置，不得猜测名称或编码。

PATCH 中未提交某个 `fieldCode` 表示不修改；`fieldValue`、`num`、`date`、`rangeDate` 传 `null` 请求清空；`options`、`appendix`、`employee` 传 `[]` 请求清空。`rangeDate` 非空时必须按开始、结束顺序恰好传两个 `yyyy-MM-dd` 字符串，`rangeDate: []` 是非法日期区间。是否允许清空仍以字段必填配置和服务端最终校验为准。

## 示例

用户要求“创建名称为测试交易方 A 的交易方”，字段配置显示：

- module 0 的 `vendorText`、`adCountry`、`vendorNature` 必填；
- module 1 的 `country`、`address` 必填；
- module 2 的 `name` 必填。

正确处理是：名称已经提供，只询问 `adCountry` 和 `vendorNature`。用户未要求创建地址或联系人，因此不询问 module 1、module 2 的字段。只有用户随后要求同时创建地址或联系人时，才检查对应子项内部的必填字段。
