# 执行契约

## 确认分级

| 场景 | 是否确认 |
| --- | --- |
| 查询、定位、人员消歧、权限预检 | 否 |
| 单条当前任务抄送给一名唯一人员 | 用户明确指令即授权，预检后只执行一次 |
| 加签、转办 | 是 |
| 当前待办的多接收人抄送 | 是 |
| 历史任务抄送 | 是，展示历史属性和选取依据后确认 |
| 批量或复合操作 | 是，只确认整套业务计划一次 |

审批通过、拒绝、完成盖章、完成归档不进入本 Skill 的确认流程；必须先路由其他 Skill。

## 业务预览

预览面向用户展示：

- 合同或合同组名称、编号；
- 当前节点和当前处理人；
- 动作顺序、接收人和加签模式；
- 原因或备注原文；
- 可执行、被拦截和待补充数量；
- 非事务、等待他人处理或终结当前责任等关键影响。

历史任务抄送还必须展示“这是历史审批任务”、任务时间以及选中该任务的业务依据；当前处理人不再作为历史任务的定位依据。

任务 ID、人员 ID、流程 ID、命令码、接口参数和请求标识只保存在内部。

用户确认绑定的是本轮业务对象、动作、人员、顺序和原因。执行前重新读取任务详情并复核：

- 业务计划未变化时，执行已确认动作，不重复询问。
- 目标、人员、模式、原因、数量或步骤发生业务变化时，停止并重新确认。
- 只有技术快照按预期更新而业务计划不变时，可继续。

“确认”“就这么办”“全部执行”等短回复，只在当前会话恰好只有一个有效预览、且中间没有修改条件时生效。否则指出冲突并请用户明确目标。

## 批量执行

1. 预览时锁定任务集合，后续新增任务不自动加入。
2. 可执行 1–20 条全部展示；超过 20 条展示汇总、前 10 条及剩余数量，并允许继续展开。
3. 用户一次确认只授权预览中明确列出的对象和数量。
4. 确认后逐条执行；每条写前重新预检，写后完成动作特定回查。
5. 允许部分成功。最终按已完成、确认未生效、待核验、失败和未执行分类列出业务对象与原因。
6. 状态失效时不自动替换成另一条最新任务，不扩大范围。

批量被中断时，不按序号推断未执行。逐项回查后分类；只有已证明未生效的项目，才能在用户重新授权后生成新计划。未知项不重放。

## 复合执行

1. 先识别加签模式，再按[动作语义](action-semantics.md)中的复合动作矩阵判断是可执行计划还是互斥请求；不得先套用“加签 → 抄送 → 转办”的固定顺序。
2. 前/后加签与转办同时出现时，在任何写入前说明冲突并让用户选择；不能先执行抄送、加签或转办中的任一步。
3. 可执行的本轮动作形成一份有序业务方案，只确认一次。并加签可在重新核验后继续；当前待办抄送必须早于转办、前加签或后加签等会让本人失去当前办理条件的动作。
4. 每步写前重新读取详情，业务内容仍一致才执行；每步写后由业务记录证明已生效，才进入下一步。
5. 已证明未生效、结果待核验、权限变化或目标变化时停止后续步骤。前一步成功不会因后一步失败而回滚；报告真实部分结果。
6. 前加签进入等待后本轮结束，不自动后台等待；任务重新回到本人待办后，剩余转办等动作必须由用户重新发起、重新定位和重新确认。

## 结果不确定

- 写请求超时或传输失败后，必须先按[页面接口契约](page-api-contract.md)只读回查。
- 回查证明已生效：按实际业务记录报告完成。
- 回查证明未生效：报告未完成，不自动重新发送。
- 仍无法证明：报告“结果暂时无法确认，已停止重复操作”，并停止后续写入。
- 不通过切换 profile、身份、通道或改用任意接口规避失败。

## 取消和变更

- 用户在写入前说取消：整套未写计划取消。
- 用户只修改某一步：更新计划并重新确认；旧计划失效。
- 已成功写入的步骤不可由本 Skill 自动撤销；后续取消只停止尚未执行的部分。
- 用户离开后回来，只有当前会话仍保留完整计划且实时核对一致时才能继续；否则重新定位和确认。
