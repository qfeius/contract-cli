# 执行契约

## 风险分级

| 场景 | 是否确认 | 执行要求 |
| --- | --- | --- |
| 查询、定位、权限预检 | 否 | 只读执行并用业务语言返回。 |
| 单条当前审批抄送给一个明确人员 | 否 | 用户明确指令即授权；内部预检后只执行一次。 |
| 审批通过、加签、转办 | 是 | 先展示动作、合同或节点、接收人及关键参数。 |
| 任意复合动作 | 是 | 展示完整有序步骤、每步影响和不可回滚边界，一次确认整套计划。 |
| 历史审批抄送 | 是 | 明确历史属性、选取依据和接收人。 |
| 多接收人抄送 | 是 | 展示接收人数和人员。 |
| 任意批量动作 | 是 | 展示业务汇总、代表性样例、可执行和拦截数量。 |

## 内部执行计划

预检后在内部形成执行计划，至少保存：

- 动作类型；
- 已解析的任务、流程、合同、节点和人员 ID；
- 接收人集合及顺序；
- 加签模式、原因或备注；
- 预览时锁定的任务快照、状态和查询时间。
- 复合计划中的步骤顺序、每一步初始预检结果、终结动作和需要等待他人处理的阶段边界。

这些信息用于防止确认后目标漂移，不作为用户确认话术。用户看到的是合同、节点、人员、数量和影响等业务信息。

运行器为每条预检生成 `planFingerprint`，覆盖动作、任务、节点、接收人顺序、加签模式、原因/备注和请求业务字段。Skill 必须保存预览时返回的值，执行时原样传入；不允许自行计算、猜测或为变更后的计划复用旧值。

## 预览内容

单笔预览至少说明动作、合同名称或编号、审批节点、接收人和关键参数。批量预览至少说明：

- 业务筛选范围；
- 命中的任务数和合同数；
- 可执行数量；
- 被拦截数量及业务原因分类；
- 接收人、加签模式或备注；
- 少量代表性合同与节点，剩余明细按用户要求展开。

预览不得用技术 ID 代替合同或节点，也不得把页面接口响应原样转发给用户。

## 批量锁定与执行

1. 预览时锁定真实任务快照，后续新增任务不自动加入。
2. 明细过多时先展示汇总和少量样例，并提供“查看全部明细”的自然入口。
3. 用户一次确认只授权预览中明确显示的可执行数量。
4. 确认后只逐条执行锁定任务；页面接口没有原子批量能力时，不宣称“一次全部成功”。
5. 允许部分成功。最终按成功、失败和未执行分类，并给出合同、节点和业务原因。

批量被进程退出、网络中断或会话中断打断时，不能用“前 4 条已完成”推导“后 6 条一定未执行”。先根据逐项写后记录把任务分成“已完成／已证明未执行／结果未知”；只允许重新处理“已证明未执行”的项目。结果未知项先查页面状态，仍无法确认时停止，不重放整批，也不按序号假定未执行。
6. 某项失效时不自动替换成另一条最新任务，也不扩大到新的合同或节点。

## 复合计划执行

1. 先为整套计划逐步预检并展示一份业务预览，用户只确认一次；用户确认绑定业务对象、有序步骤、人员和参数，不绑定用户不可见的技术快照值。
2. 按预览顺序执行。每一步真正写入前重新生成当前预览和独立指纹，再原样用于该步写入；执行后完成对应写后复查，复查通过后才进入下一步。
3. 前一步导致同一业务任务按预期从待办变为已办时，下一步可以在业务计划不变的前提下使用新快照继续。若重新预检发现合同、节点、人员、步骤或参数变化，则停止并重新向用户确认。
4. 审批通过必须最后执行；审批通过与转办不能同时作用于同一任务。后串签、后会签已经结束当前责任，也不能再接审批通过或转办；这些冲突必须在统一预览前消解，不能执行到一半才发现。
5. 前串签、前会签后需要他人先处理，当前会话把剩余步骤置为“等待协作后继续”，不轮询等待、不后台自动执行。并加签写后仍保留当前待办时，才可以继续当前责任动作。
6. 任一步失败或结果不确定时停止该任务的后续步骤。批量计划中的其他任务是否继续，以预览说明为准；默认继续其他锁定任务，但不得把失败任务换成新任务。
7. 已完成步骤不自动回滚。最终逐步列出“已完成、失败或待核验、未执行”，并说明当前审批责任或流程状态。

## 确认绑定

- 当前只有一个有效预览时，接受“确认”“执行吧”“可以”等自然确认。
- 不要求用户重复完整句子，不要求用户提供任务 ID 或请求标识。
- 同时有多个有效预览时，先让用户按动作、合同或类型等业务信息选定。
- 不主动把“两个都执行／全部执行”列为多个独立预览的确认选项。用户明确要求合并时，旧预览全部失效，先按复合动作重新校验和生成统一预览，再确认一次。
- 目标、接收人、模式、原因或数量发生变化时，旧确认失效并重新预览。
- 接收人发生变化时，必须在当前轮重新解析新人员、复检原目标并展示新预览；不能只承诺以后再查。用户附带的“确认”不能沿用旧方案，只有新预览形成后的后续自然确认才生效。
- 例外仅适用于“上一轮已经锁定唯一目标、接收人和动作顺序，并明确要求用户补齐剩余必填参数后同时确认”的连续对话：用户一次补齐全部参数并明确确认，且复检后没有产生新的候选、冲突或范围变化时，可绑定补齐后的唯一计划直接执行；否则仍需新预览确认。
- 取消是终止，不是普通参数变化。用户取消后要清除预览、指纹和授权；后续孤立确认既不能执行旧预览，也不能自动用旧参数生成新预览。只有新的明确业务指令才能重新开始。
- 运行器的 `--confirm-task-id` 是内部硬拦截，由 Skill 对每条已确认任务自动传递。
- 运行器的主硬拦截是 `--confirm-plan-fingerprint`。旧的 `--confirm-task-id` 仅保留兼容校验，不能代替完整计划绑定。

## 执行前复检

每条写入前重新读取任务状态和页面动作权限：

- 状态和权限未变：继续执行锁定动作。
- 个别任务已完成、已转交或失去动作权限：跳过该项并在结果中说明业务原因。
- 变化导致接收人、模式、动作或总体范围与用户确认内容不同：停止受影响部分；需要改变业务方案时重新预览确认。

等待时间本身不必机械地触发第二次确认；是否重新确认取决于复检后业务范围或参数是否改变。

## 单条直接抄送

单条明确抄送虽然不再追问一次“确认”，仍须完成目标唯一性、人员唯一性、本人可操作范围、页面动作权限和实时状态预检。任何条件失败都不发送；成功时只执行一次并直接报告业务结果。

如果预检发现同一接收人已有抄送记录，单条直接授权不再适用：先说明已抄送过且本轮未重复发送。用户明确说“再次抄送”后重新生成带重复授权的新预览；该预览必须把“会新增一条重复抄送记录”说清并确认一次。

多人抄送已有预览后，用户以命令式语言把接收人缩减为唯一一人时，必须废弃旧计划指纹并为新范围重新预检。新范围同时满足“当前审批、一个任务、一个唯一接收人、无歧义”时，该轮命令即为新的直接授权，可以执行；不得复用旧指纹，也不得向被删除人员发送。若用户只是要求“改方案看看”或明确只预览，则停在新预览，等待后续确认。

## 超时、重试与结果不确定

- 写请求超时或返回不确定时，先重新查询该任务的审批状态和人员变化。
- 能证明未生效时，才可在原授权范围内谨慎重试一次。
- 无法证明是否生效时，报告“结果暂时无法确认”，停止重复写入，并保留内部诊断信息。
- 已经完成页面复查但仍无法证明时，使用“已复查但结果仍待核验”；不要再次把复查交给用户或写成尚未执行的下一步。
- 不因外层请求成功就推断所有业务项成功；以页面业务响应和复查结果为准。

## 写后复查

- 转办：重新查询本人待办；原任务已移除才可把责任变化标为已验证。
- 加签：比较写前、写后的审批记录，验证本次新增加签记录的模式、人员和子任务；串签还要核对人员顺序与首位运行状态。全部一致才可表述为“已核验模式、人员和顺序”。
- 审批通过：原任务从本人待办移除，且审批记录出现本任务的通过结果，两项同时满足才可表述为“已通过”。
- 抄送：比较写前、写后的抄送记录，新增记录覆盖全部目标人员时可以表述为“已生成抄送记录并核验接收人”。`readStatus` 不为已读时不得说对方已经阅读；没有接收人侧证据时也不扩写成“对方已经看到”。
- `postcheck.status=not_verified` 时，只说明页面请求已接受但业务效果尚未完整核验，并停止自动重写；不得把未验证部分写成已确认事实。
