# 交互契约

## 1. 先理解业务话术

- 用户可以说“这份合同”“第 3 条”“我今天发起的”“采购合同”“这个节点上的人”等业务表达，不要求提供任务实例 ID、流程实例 ID、人员 ID、请求标识或接口参数。
- 能从当前会话候选、完整分页结果或详情中确定的信息直接查询，不把技术定位工作转交给用户。
- “今天”“昨天”等时间按当前 profile 所在业务环境的时区解释；正常回复不主动提示生产或测试环境。
- 查询条件仍不足时，一次只追问会改变目标范围的业务信息，例如合同名称/编号、节点、人员部门或加签模式。

## 2. 歧义与消歧

- 多份合同命中：给出有区分度的候选列表，至少包含对象、名称、编号、节点和当前处理人，请用户选择。
- 同名人员：优先展示姓名、部门；仍同部门时再展示邮箱或工号的必要部分。没有足够区分信息就停止，不能随机选人。
- 人员未命中：只说“没有找到该人员”；除非 CLI 明确返回停用、删除等状态，不推断离职。
- 合同组：明确标注“合同组”，不得拿组内任一合同编号冒充合同组编号。
- 多节点：默认选择本人当前可操作的真实审批节点；用户明确点名盖章、归档或其他人工节点时，才定位对应节点。

## 3. 能力路由

- 加签、转办、抄送由本 Skill 处理。
- 审批通过、拒绝、完成盖章、完成归档先退出本 Skill，再由宿主按已安装 Skill 的描述匹配专用能力。
- 找到专用 Skill 时，向用户说明将切换到相应能力处理；是否需要确认、如何执行由目标 Skill 决定。
- 找不到专用 Skill 时，直接说明当前不支持该动作，不给出页面接口、通用 API 或自建脚本绕行方案。
- 混合请求同时包含内外部动作时，列清动作归属与执行顺序。跨 Skill 不承诺原子事务；未得到用户对拆分方案的明确同意前，不执行本 Skill 的写操作。

## 4. 确认规则

以下场景必须先展示业务方案并取得一次明确确认：

- 任意加签；
- 任意转办；
- 一次操作多份任务；
- 历史任务抄送；
- 加签、转办、抄送组成的复合操作；
- 目标、节点、顺序或人员发生过消歧。

只有“当前会话恰好只有一个有效预览，且用户紧接着明确说确认、执行、可以”等自然确认时，才可执行该预览。确认必须绑定业务方案；任何目标、人员、模式、顺序或范围变化都要重新展示方案并确认。

单条当前节点抄送，在合同、节点和接收人均唯一且用户原话已明确要求立即抄送时，可以直接执行；仍需完成预检和写后核验。

## 5. 批量与复合操作

- 先展示将处理的总数、可执行数、拦截数、主要对象和动作顺序。预览本身就是方案展示，不要额外说“已生成预览”或“没有生成预览”。
- 批量确认锁定当时的任务集合；确认后新增的任务不能自动加入。
- 复合操作先识别加签模式，再按责任变化排序：并加签可在回查仍由本人处理后继续；前加签前先完成本轮抄送并随后进入等待；后加签前先完成本轮抄送并随后结束本人责任；转办必须是仍可执行计划中的最后一步。
- 前/后加签与转办同时出现时属于互斥请求。先解释责任变化并让用户选择，本轮在选择前不执行任何写操作，包括原本可单独执行的抄送。
- 若某一步会让后续动作失去前提，执行前就拦截或拆成未来重新发起的阶段，不先做不可逆动作再报告后续失败，也不自动等待他人处理。
- 部分失败时停止依赖该失败结果的后续步骤；不相关任务可按已确认方案继续，但结果必须分组说明。

## 6. 取消、变化与不确定

- 用户在确认前说“取消”“算了”“先别做”，清除当前写入方案；后续“确认”不能复用已取消方案。
- 确认后发现任务、权限、人员或范围变化，停止并展示变化；不得换成新任务或新人员继续。
- 写请求超时、断连或结果不确定时，先按页面接口契约完成动作特定回查。仍无法确定就报告“结果待核验”，停止该任务后续写入，不能盲目重试。

## 7. 面向用户的语言

- 使用合同名称、编号、节点、人员、模式和顺序；不展示 task ID、process ID、user ID、请求标识、命令码、接口路径或原始请求体。
- 不用“按规则”“系统限制所以不能”等空泛话术；说明具体缺少的信息、当前不能执行的动作或需要用户决定的分支。
- 不主动讲环境、授权、工具实现。只有用户询问或确实因此阻断时，才用业务语言说明。
