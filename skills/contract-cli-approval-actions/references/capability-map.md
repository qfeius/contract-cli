- Skill：`contract-cli-approval-actions 1.7.4-test`，状态 `portable-test-ready`。
- 登录依赖：`contract-cli >= 1.9.4` 的 `contract-test` User 登录态。
- 运行入口：随 Skill 完整目录分发的 `scripts/page_api.py`；不依赖业务代码仓。

- 数据与动作来源：只使用标品页面同范围能力；没有生产环境入口，也没有任意路径透传能力。

## 写能力保护

1. 写命令默认 `executed: false`，只读取实时任务和权限并生成内部请求预览；是否向用户二次确认按 [执行契约](execution-contract.md) 分级。
2. 实际写入必须同时传 `--execute` 和预览返回的 `--confirm-plan-fingerprint`；指纹绑定动作、任务、接收人和关键参数。兼容参数 `--confirm-task-id` 如传入也必须匹配。两者都不向用户展示。
3. 审批通过、加签和转办只从当前待办中反查任务；找不到、状态变化或动作权限缺失时停止。
4. 抄送从当前用户可见的待办、已办和抄送范围反查任务，并再次读取详情权限。
5. 人员查询返回标品内部 `employeeId`；动作请求不接受姓名直接写入。
6. 每个任务单独请求，批量场景不伪装成一个原子操作。
7. 默认结果只保留执行所需的最小任务摘要；接口路径、请求体和完整权限仅在显式诊断模式返回。
8. 写动作返回 `postcheck`：审批通过核验原待办移除和通过记录；转办核验原任务是否移出本人待办；加签核验新增记录、模式、人员和串签顺序；抄送核验新增发送记录与接收人，但不把发送记录解释为对方已阅读。
9. 复合动作以一次业务确认统一授权；每一步在执行前重新预览并使用当前独立指纹，随后执行和复查。前一步造成的预期状态变化不会机械触发第二次用户确认，但业务对象、步骤、人员或参数变化必须重新确认。复合动作不是单个后端事务，失败时停止未执行步骤且不回滚已完成步骤。

## 易用性约束

- 普通用户只看到合同、节点、人员、业务范围、数量、影响和业务原因；技术 ID 与请求标识默认隐藏。
- 待办表格固定使用“当前处理人”，当前用户显示为“你”；多人节点显示节点内全部未办人员，详情读取失败时显示“暂未取得”而不猜测。
- 单条当前审批抄送给一个明确人员时，用户的明确指令可以直接授权执行；审批通过、加签、转办、复合动作、历史抄送、多接收人抄送和批量动作需要业务预览。
- 当前只有一个有效预览时，自然回复“确认”“执行吧”“可以”即可，不要求复述完整确认句。
- 批量动作一次汇总确认，执行时仍逐条调用页面接口并允许部分成功。
- 待办不超过 20 条时完整表格展示；超过 20 条先给总数、分布和前 10 条，用户要求后再分批展开。
- 同名人员没有页面可验证的区分字段时停止操作；人员未找到时只报告未找到，不判断或暗示离职。唯一搜索结果可以继续使用，但不能描述为已识别或排除历史离职档案。
- 人员、目标或权限在成案前被拦截时，只回复业务动作没有执行、原因和下一步，不向用户汇报“未生成预览”等内部过程状态。
- 测试环境可在必要时提示；生产环境的正常回复不得默认展示环境名称。

## 能力不可用时

- 登录缺失或过期：提示重新完成 `contract-test` User 登录。
- 目标不唯一：展示最小必要候选，不猜测任务或人员。
- 页面未开放动作：报告缺失的真实动作权限，不尝试绕过。
- 写请求超时：重新查询任务状态；不能证明未生效时不重试。
- test 页面字段或枚举变化：停止写入，重新核对标品页面实现后更新运行器。
