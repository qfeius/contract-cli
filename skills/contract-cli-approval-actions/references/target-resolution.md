# 目标定位

底层动作只接受真实 `processTaskInstanceId`。用户不需要事先知道任务实例 ID；Skill 通过当前用户的标品任务列表解析，并把这些 ID 作为内部执行数据保存。

## 定位方式

业务对象名称按普通文本参与合同任务查询。合同或合同组名称中即使包含“飞书”“审批”“任务”“邮件”等其他产品词，也不得把名称中的词解释成新的产品意图；动作仍由句子中的“给这份合同加签/转办/抄送”等合同上下文决定。用户说“把 X 的审批抄送/转办/加签给某人”时，即使没有重复说“合同”，也先把完整 X 当作可能的合同名称查询。只有用户明确说要处理飞书原生审批、飞书审批中心或给出飞书审批实例线索时，才切换能力；合同侧查无 X 时先追问，不得自动切换或发起授权。

| 用户提供的信息 | 运行器参数 | 处理规则 |
| --- | --- | --- |
| 任务实例 ID | `resolve --task-id` | 最确定；仍需实时校验任务属于当前用户可见范围。 |
| 合同 ID | `resolve --contract-id` | 在当前用户任务中精确匹配合同业务 ID，按 `timestamp` 标出最新任务。 |
| 合同/合同组编号 | `resolve --contract-number` | 精确匹配完整编号，按 `timestamp` 标出最新任务；没有编号的合同组改用名称候选，不编造编号。 |
| 合同/合同组名称 | `resolve --query` 后在候选中校验 | 在当前用户完整可见任务集上做包含匹配；命中多条时用编号、节点、时间或类型消歧。 |
| 本人全部当前待办 | `resolve --scope todo` | 不传其他目标字段；当前用户由登录态确定。 |
| 合同类型 | `resolve --category-id` 或 `--category-number` | 二级类型精确匹配；一级类型增加 `--include-descendants`。 |
| 审批节点 | `--process-id` 加 `--node-id`，或 `--node-type approve` | 只保留同一流程和真实审批节点内属于当前用户的任务。 |

按合同 ID 或合同编号命中多个流程或任务时，先按用户动作和节点语义过滤，再按 `timestamp` 倒序。用户说“最新审批”或“最近一次历史审批”时必须增加 `--node-type approve`，不能把更新更晚的提交、归档等任务当成审批。`latestTaskId` 只在内部使用；执行前用业务语言说明节点、时间和选取依据。

用户仅说“这个合同”“某合同”并要求加签、转办或抄送，且没有明确其他人工节点时，将其理解为处理审批流中的真实审批节点：先用 `--node-type approve` 或等价本地过滤得到候选，再生成面向用户的连续序号。盖章、归档等节点只有在用户明确指定“当前任务”或真实节点名称时才进入候选；不能把它们与默认审批候选混排。

名称查询先做标准化后的完全匹配判断。若恰好一个候选的完整名称与用户提供名称一致，而其他候选只是前缀、后缀或带“副本”等包含匹配，则使用唯一完全匹配项；不要因为包含结果更新时间更晚而选择它，也不必制造无意义的二选一。多个候选都完全匹配时，才用编号、节点、时间或类型让用户消歧。

合同类型名称按页面保存的完整文字做区分大小写的精确匹配。“E签宝”和“e签宝”是两个不同业务类型；用户输入与其中一个完整名称逐字一致、且类型编号和父类型均可唯一核实时，使用该精确类型并向用户说明排除了另一个。用户只给出大小写不明确的模糊名称、或多个类型的完整名称无法唯一时，展示类型名称、编号、父类型和层级供选择。

## ID 从哪里来

- `processTaskInstanceId`：来自 `tasks` 或 `resolve` 响应中的真实任务列表；写命令使用 `--task-id` 传入。
- `employeeId`：使用 `employees --keyword` 从标品人员选择器查询；同名时按部门、邮箱等信息消歧。
- 合同/合同组 ID 和编号：来自任务列表的 `businessId` 与 `contractNumber`，也可由用户直接提供后精确匹配；合同组编号为空时不使用组内合同编号替代。
- 流程与节点 ID：来自任务列表的 `processInstanceId`、`taskNodeId`；节点名称只用于向用户展示。
- 合同类型 ID 和编号：来自 `categories` 或任务列表的 `contractCategoryId`、`contractCategoryNumber`。

不要让用户手工猜内部 ID，也不要把姓名、节点名或类型名直接当作动作参数。

## 用户展示边界

- 任务、合同、流程、节点、类型和员工 ID 只用于内部精确定位、预检和调用页面接口。
- 待办列表、候选选择、范围预览和结果使用合同名称、合同编号、节点名称、人员姓名、部门、邮箱、时间和状态等业务字段。
- “选择最新任务”要解释为“选择了该合同最近发起或最近更新的审批”，不要显示 `latestTaskId`。
- 人员重名时用姓名、部门和邮箱消歧，不展示 `employeeId`。
- 同名人员的部门、邮箱和员工编号都为空或相同时，页面当前没有可核验的消歧依据，应直接停止并说明需补全人员资料，或改用另一位页面能够唯一检索的人员；不要继续索取页面已经证明未维护的字段，也不用内部 ID 让用户选择。接收人未解决前，不收集合同、节点、模式、原因等后续参数。用户要求随机选择时拒绝并结束。搜索无结果只表示未找到，不能推断人员离职；唯一搜索结果也不能被描述为“排除了历史离职档案”。
- 只有用户主动要求技术详情或排障需要时，才按 [输出契约](output-contract.md) 展示最少必要的 ID。

## 多任务规则

- 加签、转办只使用 `todo` 中的运行中任务。
- 抄送优先使用当前任务；无当前任务且用户明确要历史审批时，从 `done` 中先筛选真实审批节点，再按时间定位最新历史审批并强制预览。
- “本人全部当前待办”只包含预览时锁定的任务；不带入预览后新增任务。
- 执行前任务状态变化时，该项失败；不得自动寻找另一条“最新任务”替换。
- 类型批量场景先用 `categories` 明确层级，再用 `--include-descendants` 展开一级类型。

## 冲突拦截

- 多种定位信息不能证明指向同一对象时，展示冲突并要求用户确认。
- 使用节点定位时必须同时锁定流程实例，避免同名节点跨流程误命中。
- 只给合同或合同组名称、节点名称、类型名称或人员姓名且结果不唯一时，不调用写能力。
