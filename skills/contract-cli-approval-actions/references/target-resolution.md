# 目标定位

底层页面写请求使用真实任务实例，但用户不需要知道任务 ID。Skill 通过当前 User 的标品任务列表和流程详情内部衔接。

## 完整任务集

按照[页面接口契约](page-api-contract.md)从第 0 页完整读取任务。查询本人全部任务时不传业务类型过滤；分页完成后再按用户条件筛选，不能用旧的单类型任务接口代替。

## 定位优先级

| 用户信息 | 处理规则 |
| --- | --- |
| 本轮已经选定的序号 | 只使用当前候选快照；筛选或重新查询后旧序号失效 |
| 合同 ID、任务 ID | 仅内部或用户主动提供时精确匹配，仍需核对当前 User 可见性和状态 |
| 合同/合同组编号 | 完整精确匹配；命中多个流程时再按节点和时间消歧 |
| 合同/合同组名称 | 先做标准化完全匹配，再做包含匹配；唯一完全匹配优先 |
| 合同一二级分类 | 用分类树解析目标 ID 与后代范围，直接过滤 v3 任务列表中的分类 ID；普通合同和合同组使用同一规则 |
| 节点 | 同时锁定流程和真实节点，不能用同名节点跨流程匹配 |
| 本人全部待办 | 使用完整 `todo` 集合，预览后新增任务不自动加入 |

合同或合同组名称中的“审批”“任务”“飞书”等词只是名称的一部分，不能据此切换产品。只有用户明确说飞书原生审批、飞书审批中心或给出飞书审批实例线索时，才路由飞书审批能力。

## 节点语义

- 普通“查我的待办”使用完整 `todo`，可包含提交、审批、盖章、归档等人工节点；明确“审批待办/审批节点”则只保留已确认的真实审批节点。分类、合同组等条件与节点条件取交集后再计数、排序、连续编号，不把其他节点混入结果后请用户二次筛选。无法确认类型的行单独说明，不能猜为审批并纳入写入范围。
- 用户只说“给这个合同加签/转办/抄送”时，默认筛选真实审批节点。
- 用户说“最新审批”“最近一次历史审批”时，先筛选审批节点，再按时间倒序；不能把更新更晚的提交、盖章或归档任务当成审批。
- 提交、盖章、归档等节点只有在用户明确说出真实节点名称或明确表示“当前任务”时才进入候选，并且只允许 CLI 实时开放的辅助动作。
- 本 Skill 不完成审批通过、拒绝、盖章或归档。遇到这些业务动词先退出本 Skill并路由其他能力。

## 多流程和历史任务

- 同一合同有多个审批实例时，不能只按合同最新更新时间选任务；先按动作、节点、状态过滤，再使用用户明确的“最新/历史”口径。
- 加签、转办只使用本人当前待办：目标记录必须仍未完成且当前登录用户仍是处理人。
- 抄送默认使用本人当前待办；用户明确要求历史审批抄送时，从已办中筛选真实审批节点，展示时间和选取依据并确认，不能把任意最新任务当作用户指定任务。
- 用户明确要求对已办或历史审批执行加签、转办时，本 Skill 不生成写入候选；说明该任务已不在本人责任内。
- 任务状态变化时该项失效，不自动替换成另一条最新任务。

## 合同分类定位

分类树节点提供 `id`、`name`、`categoryNumber`、`abbreviation`、`parentId`、`depth`、`enabled` 和 `subCategoryNodeList`。按分类筛选时：

1. 从分类树按名称、编号、缩写和父级消歧，得到唯一分类 ID。二级类型默认只取自身；一级类型在用户表达“这个类型下全部”时递归展开 `subCategoryNodeList`，目标集合包含根节点和全部后代。
2. 用户说“只包含启用分类”时，对目标集合逐节点保留 `enabled=true`，排除 `enabled=false`；字段缺失的节点状态未知，不能擅自当作启用。
3. 完整读取 v3 任务列表后，优先按每条任务的 `contractCategoryId` 与目标 ID 集合直接过滤。普通合同和 `businessTypeCode=10` 的合同组都走这条链路，不经过合同搜索。
4. 任务缺少分类 ID 时，先从该任务详情补取分类 ID、名称或编号。普通合同仍缺失时，可用 CLI 已有的 `contract search`，按 `combine_condition.contract_category_name` 或 `contract_category_abbreviation` 查询目标分类，再用任务业务对象 ID 做辅助匹配。
5. `contract search` 不能用于 `businessTypeCode=10` 的合同组，也不能作为任务存在性或分类命中的必要条件。搜索为空只表示该搜索未命中，不能推出任务不存在。
6. 页面详情和允许的辅助查询都无法确认分类时，将任务标为“分类未确认”。这类任务不能静默排除后仍声称结果完整，也不能未经证明纳入分类批量写入。

## 人员定位

人员通过页面人员选择器查询，并在执行前按 ID 复核：

1. 唯一可选结果可直接采用。
2. 同名多条先展示姓名和部门；部门仍相同再补邮箱或工号。
3. 仍无差异时停止，不让用户按“第一个/第二个”盲选，也不索取内部 ID。
4. 用户随机选择、随便选一个时拒绝。
5. 搜索无结果只说没有找到；不能推断离职。接口明确返回状态时按原状态说明。
6. 只有当前选择器返回且按 ID 复核可选的记录可成为正式接收人。别的任务历史中出现的人、当前查询未返回的人，不能借近音姓名或历史 ID 加入候选；可请用户纠正准确姓名后重查。

## 冲突处理

- 合同编号、名称、分类、节点等条件不能证明指向同一对象时，展示最少必要差异并追问。
- 一条请求同时包含本 Skill 与其他 Skill 的动作时拆分归属；没有得到用户对拆分处理的明确同意前不写入支持部分。
- 任何写入前都重新核对任务、流程、节点和人员仍与确认时一致。
