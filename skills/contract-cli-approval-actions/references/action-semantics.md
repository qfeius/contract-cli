# 动作语义

本页只定义加签、转办、抄送。审批通过、拒绝、完成盖章和完成归档必须退出本 Skill 后路由其他能力。

## 加签

| 模式 | 业务含义 | 人数 |
| --- | --- | ---: |
| `parallel` | 加签人与当前处理人共同审批 | 至少 1 人 |
| `before_serial` | 加签人依次处理，完成后回到当前处理人 | 至少 1 人 |
| `before_parallel` | 加签人全部处理后回到当前处理人 | 至少 2 人 |
| `after_serial` | 当前责任结束后，加签人依次处理 | 至少 1 人 |
| `after_parallel` | 当前责任结束后，加签人全部处理 | 至少 2 人 |

- 加签原因必填，不替用户编写原因。
- 同一动作内人员去重后再校验人数；串签保留用户顺序，不排序。
- 当前用户、当前节点已有处理人或页面返回不可选的人员不能再次加签。
- 前/后加签的“被加签人”不得再加签：读取目标节点当前记录（`processRecords.todo[].records[]` 中与 `taskNodeId` 匹配且 `taskStatusCode=0` 的记录）的 `parentCommandTypeCode`；当其为 `18`（后串签）、`19`（后会签）、`20`（前串签）、`21`（前会签）时，当前用户是本次前/后加签的被加签人，停止加签，不生成方案、不写入。
- 加签只对本人当前待办生效：目标记录须同时满足 `taskStatusCode=0` 且 `assigneeEmployees[].employeeId` 包含 `task.permissions.employeeId`；否则停止写入，并说明该任务已不在本人责任内。
- 节点要求发起人选择加签人编辑权限时才追问；固定权限不重复询问。
- `parallel` 写后回查证明任务仍可操作时，才能继续转办或抄送。
- `before_serial`、`before_parallel` 会进入等待他人处理阶段，本轮后续责任动作停止。
- `after_serial`、`after_parallel` 已结束当前责任，不能在原复合计划中继续转办或按当前待办抄送；后续如需抄送，必须按历史任务重新定位并确认。

## 转办

- 只有一个接收人，不能是当前用户。
- 多人节点只转移当前用户自己的责任，不改变其他人的责任。
- “把我的全部审批转给某人”只处理预览时锁定的本人当前待办。
- 业务说明可选；用户没有给出时不追问。
- 写后必须证明责任转给指定人员；原待办消失、节点结束或流程变化都不能单独作为成功证据。

## 抄送

- 至少一名接收人，不能包含当前用户；同一请求重复人员按首次出现去重并告知。
- 抄送不改变审批责任，也不等于对方已读。
- 备注可选；不为备注增加追问。
- 详情完整且已有同一任务同一接收人的抄送记录时默认拦截；只有用户明确说“再次抄送”“重新提醒”才可生成新的重复发送方案。详情不完整时不能据此声称“未重复”，也不能写入。
- 抄送附件不属于本 Skill；先路由其他能力，找不到则说明不支持。
- 抄送分两类：本人当前待办抄送，以及用户明确指定的历史任务抄送。
- 当前待办抄送：目标记录须同时满足 `taskStatusCode=0` 且当前登录用户属于 `assigneeEmployees[]`；否则不按当前待办生成方案。
- 历史任务抄送：用户明确要求对某个历史审批任务抄送时，从已办记录（`processRecords.done`）中筛选真实审批节点，展示时间和选取依据并确认；不能把任意最新任务当作用户指定任务。历史任务的详情仍须完整、且确认该节点仍开放抄送，才可生成方案。

## 节点范围

- 默认合同加签、转办、抄送只定位真实审批节点。
- 用户明确指定提交、盖章、归档等其他人工节点时，只有页面详情确认该节点开放目标辅助动作才可继续。
- 本 Skill 永远不完成审批通过、拒绝、盖章或归档动作。
- 前/后加签产生的子任务中，当前用户作为被加签人时，不再触发加签动作（`parentCommandTypeCode` 为 `18/19/20/21`）。
- 未知人工节点、服务节点、网关和自动节点不操作。

## 复合动作

复合计划没有统一固定顺序，必须先根据加签模式判断每一步执行后本人是否仍持有当前任务：

| 动作组合 | 本轮可执行顺序 | 处理规则 |
| --- | --- | --- |
| 抄送 + 转办 | 抄送 → 转办 | 转办必须最后执行 |
| 并加签 + 抄送 | 用户已明确顺序时按其顺序；未明确时并加签 → 抄送 | 并加签写后必须重新读取任务，仍属于本人且抄送权限仍在才能继续 |
| 并加签 + 转办 | 并加签 → 转办 | 并加签写后仍属于本人且转办权限仍在才能继续；转办最后执行 |
| 并加签 + 抄送 + 转办 | 并加签 → 抄送 → 转办 | 每一步写后重新核验；转办必须最后执行 |
| 前加签 + 抄送 | 抄送 → 前加签 | 前加签后进入等待，本轮结束 |
| 后加签 + 抄送 | 抄送 → 后加签 | 后加签后本人责任结束，本轮结束 |
| 前加签 + 转办 | 不可组成同一轮即时计划 | 两者执行后都会使另一动作失去本人当前待办前提；写入前让用户二选一 |
| 后加签 + 转办 | 不可组成同一轮即时计划 | 两者都是当前责任的终结动作；写入前让用户二选一 |

- 前/后加签、转办发生互斥时，在用户选择前不得先执行其中的抄送或其他写操作。
- 用户明确要求的顺序不可执行时，说明是哪一步会使后续动作失去前提，并让用户选择；不能静默改序。
- 前加签完成后不自动等待加签人处理，也不承诺稍后自动转办；任务重新回到本人待办后，由用户重新发起剩余动作。
- 转办之后如需抄送，按“历史任务抄送”重新定位并确认，不并入原复合计划。
- 混有审批通过、拒绝、完成盖章或完成归档时拆分能力归属，不把它们纳入本 Skill 的统一确认。
- 复合操作不是事务。前一步成功、后一步失败时不回滚，按真实状态逐步报告。
