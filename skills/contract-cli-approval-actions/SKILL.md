# 智书合同加签、转办与抄送

只处理当前 `contract-cli` User 身份可见、可操作的智书合同任务。用户提供业务目标；任务、流程、节点、合同和人员标识由 CLI 查询衔接，普通回复不展示技术 ID。

## 能力路由

在调用工具前拆出全部动作：

- 本 Skill 支持查询、加签、转办、抄送，以及由这三类动作组成的可执行复合计划。
- 审批通过、拒绝、完成盖章、完成归档不属于本 Skill。先退出本 Skill，匹配宿主已安装且描述明确支持该动作的专用 Skill；找到后由该 Skill 独立判断和执行，找不到就直接说明当前不支持。
- 混合请求包含本 Skill 与其他 Skill 的动作时，明确拆分归属，不把外部动作伪装成本 Skill 能力，不静默删除任何一步，也不承诺跨 Skill 事务。只有用户明确同意先处理本 Skill 支持的部分时才继续。
- 用户要求代另一位审批人办理、处理“某人的全部审批”或指定其他操作者时直接停止；只能处理当前登录用户本人的责任。
- 撤回、催办、终止、修改流程定义、抄送附件等未声明能力同样先路由专用 Skill；没有匹配能力时说明不支持。

承诺任何本 Skill 之外的动作前，必须找到当前宿主实际安装、且明确声明支持该动作的 Skill，并读取对应说明。没有证据就不承诺，也不在拦截、完成或闲聊结尾主动推荐“我可以催办”等能力。审批通过/拒绝不能作为催办的替代方案。

人员查无结果只表示“没有找到该人员”，不能推断为离职。接口明确返回停用、删除或其他状态时，才可陈述该状态。

## 依赖与读取顺序

- 查询、分页、页面接口和写后核验先读[页面接口契约](references/page-api-contract.md)。
- 定位合同、合同组、分类或节点时读[目标定位](references/target-resolution.md)。
- 加签、转办、抄送或复合操作时读[动作语义](references/action-semantics.md)和[执行契约](references/execution-contract.md)。
- 组织候选、确认与结果时读[交互契约](references/interaction-contract.md)和[输出契约](references/output-contract.md)。
- 首次运行、授权异常或跨 Agent 平台安装时读[可移植运行契约](references/portable-runtime.md)。

本 Skill 不携带 Python、Node、Shell 等业务运行器，不读取凭据文件，不使用 curl，也不接受用户提供的 URL 或任意接口路径。只能调用页面接口契约列出的相对路径；`api call` 是 CLI 管理登录态的受控传输通道，不是任意接口兜底。

普通业务运行由 Agent 每次直接调用一条本契约允许的 CLI 命令；不新增批量接口或编排器。禁止脚本文件、`python -c`、`node -e`、Shell `for/while`、`xargs`、管道和重定向承担查询编排、解析或核验，也不自建临时业务数据文件。以 Shell 启动单条 CLI 命令可以；把业务逻辑写进 Shell 不可以。宿主自动归档的 CLI 结果可用宿主只读工具完整读取，见[可移植运行契约](references/portable-runtime.md)。

## 开始前检查

默认使用生产 `contract` profile。只有用户明确处于测试或验收环境时才使用 `contract-test`；同一计划的查询、人员解析、预览、写入和回查必须保持同一 profile、租户和 User 身份。正常业务回复不主动展示环境或授权实现。

首次使用先确认 `contract-cli api call --help` 真实支持 `--channel web`、`--as user` 和相对 `/open-web/web/**` 路径。缺少该能力时停止，不改用脚本、curl、浏览器抓包或直接 HTTP。

安装验收必须确认本 Skill 已进入宿主技能目录、当前会话已加载，且规则版本为 `3.1.7`（同时保存在 `version` 与 `metadata.skill_version`）。CLI 安装成功或 CLI 自身版本号不能替代该检查；更换规则后使用能加载新规则的会话。正常业务回复不汇报版本号。

## 业务主线

1. **读取完整任务范围。** 使用页面任务中心 v3 列表从第 0 页开始完整分页。“查询本人全部任务”时，必须分别对 `todo(0)`、`done(1)`、`notice(2)` 三类完整分页，再按任务实例去重，并逐类校验累计唯一数与总数；只关心待办时明确只读 `todo(0)`。加签、转办只使用 `todo(0)`；历史任务抄送从 `done(1)` 中定位真实审批节点；知会/抄送记录关注 `notice(2)`。查询本人全部任务时不暗加业务类型过滤。
2. **解析业务目标。** 按用户给出的合同、合同组、编号、分类、节点、时间或自然语言指代筛选。普通“我的待办”保留所有可见人工节点；明确“审批待办/审批节点”则先排除盖章、归档等其他节点，再计数、排序和编号。默认合同加签、转办、抄送只定位真实审批节点；其他节点须明确指定。分类查询与合同组查询也执行相同过滤，不先混入无关节点后让用户排除。
3. **解析人员。** 使用标品人员选择器查询候选，保留姓名、部门、邮箱、工号和可选状态。同名时用可核验业务信息消歧；仍不能唯一则停止。
4. **核对可执行性。** 使用标品任务详情检查详情完整性、当前状态、节点类型、本人责任、动作权限、重复抄送和人员可选性。搜索命中不等于可写；详情不完整不得写入。
   - **先做参数完整性与人数校验**：加签目标、模式和原因均为必填；模式没有默认值，不能替用户默认并加签。缺少多项时同一轮一次问全，未补齐前不说“全部通过/可以执行”。前会签、后会签去重后必须至少两人，只有一人时请用户补第二人或改为对应串签，不成案、不请求确认、不写入、不静默降级。
   - **被加签人不得再加签**：按页面接口契约先锁定本人承担的目标节点当前责任记录，再检查该记录的 `parentCommandTypeCode`；为 `18/19/20/21`（前/后串签或会签子任务）时，直接停止加签，不成案、不写入。不能用同节点其他人的记录推断本人是被加签人。
   - **加签、转办只对本人当前待办生效**：目标记录必须同时满足 `taskStatusCode=0` 且 `assigneeEmployees[].employeeId` 包含 `task.permissions.employeeId`；否则停止写入，并说明该任务已不在本人责任内。
   - **抄送按任务状态分流**：当前待办抄送执行相同的本人责任校验；用户明确要求对历史审批任务抄送时，从已办记录中定位真实审批节点，展示任务时间和选取依据并确认。详情不完整、节点未开放抄送或无法唯一定位时不写入，不能自动改选同合同的最新任务。
   - **复合动作先判断加签模式**：并加签写后仍由本人处理时，重新核验后才可继续抄送、转办，且转办必须最后执行；前加签会立即进入等待，后加签会立即结束本人责任，因此抄送必须放在前/后加签之前，而前/后加签与转办不能组成同一轮即时计划。存在互斥时先让用户选择，本轮任何一步都不执行。
5. **形成业务方案。** 展示合同、节点、当前处理人、动作顺序、接收人、关键参数、可执行与拦截数量。除执行契约允许直接发送的单条抄送外，只请求一次业务确认。
6. **逐步执行并回查。** 用户确认后、每次写入前，必须重新取得该步所需的最新任务、详情及人员证据；预览前的缓存不能替代。按[执行契约](references/execution-contract.md)完成“最新只读核对 → 单次写入 → 新的只读回查”。历史抄送只免除本人当前待办条件，不免除写前重读。各动作参数独立保存，用户只给加签的原因不能带入转办或抄送。
7. **报告真实结果。** 按已完成、确认未生效、待核验、失败和未执行分类。结果不确定时停止后续写入，不自动重试或切换通道。
8. **发送前做业务输出校验。** 普通业务回复只允许出现合同或合同组、编号、节点、人员姓名、动作、数量、时间和业务结果；发现技术字段名、命令码、接口路径、原始布尔值、临时脚本名、堆栈或原始 JSON 时，必须重新按[输出契约](references/output-contract.md)生成回复，不能直接发送或只做局部遮盖。

## 查询我的待办

用户只说“查我的待办”“有哪些待办”“继续看”“第 N 条”，且没有飞书任务、项目或截止日期语义时，直接查询智书合同任务，不让用户补技术条件。

“查我的待办”固定对应 `todo(0)`；用户明确说“查我全部任务/历史已办/知会”时，按业务主线的三类覆盖口径分别读取，不把三类混成一个待办列表。

固定展示六列：序号、对象、名称、编号、当前节点、当前处理人。

- 1–20 条全部展示；超过 20 条先展示分布、前 10 条和剩余数量。
- “继续看”沿用同一候选快照和连续序号；筛选或重新查询后重新编号。
- 合同组标为“合同组”；没有编号时留空，不使用组内合同编号代替。
- 当前处理人只来自目标节点真实未办人员，节点内已经完成处理的人不计入；超过三人压缩为“你、某某等 N 人”，用户要求时再展开。无法区分未办与已办人员时显示“暂未取得”，并停止依赖该详情的写操作。
- 批量列表必须逐行完成目标节点详情解析后再汇总；不能先把每行默认写成“你”，也不能用任意一条详情、候选人员或全流程人员批量填充其他行。
- 普通查询、分类/合同组筛选和合同候选统一使用六列；表格生成前逐行核对对象、节点、处理人及来源绑定，详见[输出契约](references/output-contract.md)。业务类型“修改合同表单”等不是“对象”列的取值。
- 空结果只表示当前 User 的本次完整查询没有任务，不表示租户全量不存在。

用户追问“他读了吗”“现在谁处理”等动态状态时，在当前轮重新查询该目标详情。候选快照只用于序号与范围绑定，旧响应只用于比较，不能当作最新状态，见[页面接口契约](references/page-api-contract.md)。

## 完成标准

- 查询：完成 0 基分页、全业务类型覆盖、去重和总数一致性检查后，才可说“全部”。
- 写入：页面写请求业务成功且动作特定的写后记录证明目标、人员和模式正确，串签还要证明顺序、并签/会签还要证明并行关系，才报告完成；HTTP 2xx 或接口 `success=true` 单独都不构成完成。
- 抄送成功只表示已发送，不等于对方已读。
- 转办成功必须证明责任转给指定人员，不能只凭本人待办消失。
- 批量或复合操作逐条列出失败、待核验和未执行项，不把部分成功说成全部成功。
- 技术 ID、命令码、请求参数、请求标识、接口路径、profile 和原始错误只保留在工具上下文，不进入普通业务回复。
