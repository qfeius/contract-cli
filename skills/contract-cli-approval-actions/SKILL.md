# 智书合同审批复合动作

## 先行硬停止

以下判断在任何“可以”“我先核对”、缺参追问、待办查询或方案说明之前完成：

- 所有用户可见回复都直接说业务事实、缺少的信息和下一步。禁止说“按合同审批流程/规则/规范/Skill 处理”“先核对规则/确认要求”等内部过程话术；追问时直接问缺少的业务信息，执行时直接说要核对或变更的合同、节点和人员。

- 同名接收人的部门、邮箱、工号都无法区分：只回答“无法安全区分，因此没有执行；请管理员补全人员资料，或换一位可唯一检索的人员”。到此结束，不再问合同、节点、方式、原因，也不再索取部门、邮箱、工号、手机号、名片、open_id 或员工 ID。
- 请求代张三或其他审批人操作：直接说明只能由本人登录处理，不查询对方任务，也不说需要再校验代办权限。
- 请求含抄送附件、拒绝、撤回、催办、终止或修改流程：首句说明不支持部分和本轮零变更，等待用户明确删除该部分；不先承诺“可以”。
- 同一任务同时含审批通过和转办，或后串签/后会签后又要求通过/转办：首句说明动作冲突并让用户选择，本轮零写入。
- 写请求超时或结果不确定：先由 Agent 复查审批记录；复查后仍无法证明是否生效时停止重复提交，直接说明“已复查但结果仍待核验”。不要把刷新页面、确认是否收到或判断是否生效转交给用户。

这是一个可独立安装的 Skill 包：目标 Agent 只需要安装 `contract-cli` 和本 Skill 完整目录，不依赖智书合同业务代码仓。Skill 随包运行器读取当前设备 `contract-cli` 的 `contract-test` User 登录态，并调用 test 环境标品页面已经使用的查询与动作接口。只处理当前用户在标品页面可见且可操作的范围。

## 待办查询路由

- 用户只说“查一下我的待办”“我有哪些待办”“继续看”或“第 N 条”且没有飞书任务、任务清单、项目任务、截止日期等明确语义时，使用本 Skill 查询智书合同审批待办。
- 用户明确说“飞书任务”“任务清单”“项目待办”或给出飞书任务链接时，不使用本 Skill。
- 查询待办属于只读操作，不需要确认；必须直接调用 `task-list` 并使用其固定六列表格，不得让 Agent 先查 `tasks`、再提取全部任务 ID 调 `task-table`，也不得因飞书任务身份或授权状态中断合同审批查询。

## 运行入口

运行器为 [scripts/page_api.py](scripts/page_api.py)。先读 [可移植运行契约](references/portable-runtime.md)、[页面接口运行契约](references/page-api-contract.md) 和 [能力清单](references/capability-map.md)。所有命令都以本 Skill 安装目录为工作目录执行，不假设存在项目仓库或固定用户路径。

- 首次运行检查：`python3 scripts/page_api.py runtime-check`
- 登录检查：`python3 scripts/page_api.py auth-check`
- 格式化当前待办：`python3 scripts/page_api.py task-list [--page-index 1]`
- 原始任务查询与筛选：`python3 scripts/page_api.py tasks --scope todo`
- 目标定位：`python3 scripts/page_api.py resolve ...`
- 人员解析：`python3 scripts/page_api.py employees --keyword <姓名或邮箱>`
- 任务权限：`python3 scripts/page_api.py task-detail --task-id <任务ID>`
- 最终候选表：`python3 scripts/page_api.py task-table --task-id <任务ID> [--task-id <任务ID> ...]`
- 写动作：`approve`、`endorse`、`transfer`、`notice`。默认只返回请求预览，不写入；复合动作由 Skill 将这些页面原子动作编排为一个业务计划。

脚本路径按当前 Skill 目录解析，不假设工作区路径。默认 profile 为 `contract-test`；只有环境标记为 `test` 且默认身份为 `user` 才能运行。

## 工作方式

0. 在发送第一句过程提示或调用任何接口前，先过三道业务闸门：
   - **不支持项闸门**：先拆分用户句子里的全部动作。审批通过、加签、转办、抄送可以进入同一个复合计划；拒绝、撤回、催办、终止、修改流程定义和抄送附件仍不支持。混入不支持项时，第一句先说明具体哪部分不支持、本轮没有执行，并询问是否删除该部分后继续；用户答复前不查询、不预览、不执行，也不承诺改用飞书消息等范围外能力代发。
   - **操作者闸门**：用户要求处理“张三的审批”“某人的全部审批”等他人责任时，立即拒绝并说明需本人登录；不先查对方任务、不说“再校验是否有代办权限”，也不接受操作者 ID。
   - **接收人闸门**：请求已经给出加签人、转办人或抄送人时，先解析人员。人员未找到、同名无法安全区分，或页面明确标记为锁定/不可选时先停止，不继续查目标或收集其他参数，更不能进入确认。搜索未返回人员只表示“未找到”，不得推断或宣称对方已经离职。
1. 识别用户要审批通过、加签、转办、抄送还是多个动作的组合，以及普通合同、合同组、类型、节点、任务或“本人全部待办”等范围。
   - 用户已给接收人、但目标尚未给出或明显不唯一时，优先解析接收人。若同名且页面没有任何可用区分字段，立即硬停止，不再查询全部待办或收集其他参数。
   - 用户只说“这个合同”“某合同”并要求加签、转办或抄送，没有明确盖章、归档等节点时，默认只在真实审批节点中列候选；其他人工节点不混入候选表。只有用户明确说“当前任务”“盖章节点”“归档节点”等时，才按真实节点和页面权限处理。
   - 加签请求缺少两个或三个必填项时，在同一条回复中把所有缺项一次问全，不逐轮盘问。目标、方式和原因都缺少时，展示候选后集中请用户补齐“序号/名称/编号 + 加签方式 + 原因”；目标已经由上下文唯一锁定而方式、原因都缺少时，同一轮同时追问方式和原因。若当前没有可展示候选，也仍集中询问；例如：“请说明并加签/前串签/前会签/后串签/后会签，并补充原因。”
   - “并加签”本身就是完整的 `parallel` 模式。用户已经说“并加签”时，不再追问前加签还是后加签；只补尚缺的目标或原因。
   - 已唯一解析加签人后，候选表只展示该人员可被新增的任务；如果加签人已经是该节点当前处理人，该任务在展示前直接排除。候选数量必须等于实际可选行数，不把不可选项放进表格后再提示用户避开。
2. 读 [目标定位](references/target-resolution.md)，用页面查询把名称和编号解析成真实 `employeeId`、合同 ID、流程 ID 和 `processTaskInstanceId`。不唯一时按 [交互契约](references/interaction-contract.md) 追问。
3. 读 [动作语义](references/action-semantics.md)，校验人数、模式、动作先后、本人操作边界和备注。复合动作必须先形成有序步骤；不得把用户说出的多个动作任选一个执行。
   - 转办说明和抄送备注都是可选项；用户未提供时直接省略，不得为了可选说明或备注增加追问轮次。追问只补齐决定目标、接收人、加签方式、加签原因或执行冲突所必需的信息。
   - 同一任务的审批通过与转办都是终结当前责任的动作，不能进入同一计划；先请用户二选一。
   - 前串签/前会签会先交给加签人，后续转办或通过进入等待态；后串签/后会签本身已经结束当前用户的原待办，不能再追加一次通过或转办。遇到这些冲突先说明并让用户调整，本轮不写入。
   - 并加签后只有实时复查证明当前任务仍可操作，才可继续抄送、转办或通过。
4. 对每个候选任务读取页面详情中的 `permittedFunctions`；页面未开放目标动作时拦截。
5. 按 [执行契约](references/execution-contract.md) 判断是否需要二次确认：目标和接收人唯一的单条明确抄送可以直接执行；审批通过、加签、转办、任何复合动作、历史抄送、多接收人抄送及任何批量动作先展示业务范围摘要。一个复合计划只确认一次。
   - 批量方案在确认问题之前固定给出命中任务数、涉及合同数、可执行数和拦截数；即使拦截数为 0 也明确写出，不能只写“共 N 条、M 个动作”。
   - 用户按一级合同类型处理时，必须展开全部启用子类型，并在汇总中按实际命中的子类型列出任务数；不能只说“已包含全部子类型”却不展示范围分布。用户明确给出二级类型时仅使用完全匹配的该类型，不因同名或大小写近似自行扩展。
6. 当前只有一个有效范围预览时，用户回复“确认”“执行吧”“可以”即可确认；Skill 在内部把回复绑定到已锁定的动作、任务集合、接收人和参数，不要求用户复述整句话或技术 ID。
   - 上一轮已经锁定唯一目标、接收人和动作顺序，只差加签方式、原因等必填参数，且已明确告诉用户“补齐这些信息并确认即可执行”时，用户在同一条消息中补齐全部参数并说“确认／执行”可直接视为对补齐后唯一计划的一次确认。执行前仍要完成冲突和实时状态复检；补齐内容造成动作冲突、范围变化或出现新的选择项时不得执行，改为说明冲突或重新展示方案。
   - 同时存在多个独立方案而用户只说“确认”时，只让用户按业务名称选择一个已有方案；不得主动提供“两个都执行／全部执行”选项，也不得把多个旧方案临时拼成新计划。用户主动要求合并执行时，重新校验动作冲突、生成一份新的统一方案并再次确认。
   - 接收人姓名被更正或替换时，旧人员解析和旧方案立即失效，必须在当前轮次重新执行人员查询和目标复检。只有新接收人唯一可选且目标仍有效时才当轮生成并展示新方案；不能只说“稍后重新核对”。新接收人未找到或仍有歧义时直接停止，绝不请求确认。
7. 一次确认绑定完整有序步骤、任务集合、人员和参数。复合计划中的每一步在真正执行前都重新生成一次当前技术快照预览，并原样传入该步最新的 `--confirm-plan-fingerprint`；这是对已确认业务计划的实时复检，不向用户展示指纹。前一步导致任务从待办转为已办等预期状态变化时，只要业务对象、步骤、人员和参数完全未变，可以更新该步指纹后继续；任一业务要素变化都必须整套重新预览确认。不能自行计算、猜测或复用过期指纹。
8. 复合计划逐步执行，不宣称原子事务：每一步写后复查通过才进入下一步；失败、结果不确定或状态不再允许时停止后续步骤。最终按“已完成／失败或待核验／未执行”列出每一步。加签核验模式、人员及串签顺序，审批通过核验原待办移除和通过记录，抄送核验新增发送记录与接收人，但不把“已发送”说成“对方已阅读”。
   - 只要步骤结果不确定，同一条回复必须列齐整套计划的三个状态：哪些已完成、哪一步待核验、哪些尚未执行。先由 Agent 重新读取页面记录，不把“请你确认对方是否收到”当作默认排查办法；页面仍无法证明时如实保持待核验并停止后续写入。
9. 查询待办和展示动作候选时按 [输出契约](references/output-contract.md) 输出。普通待办查询直接使用 `task-list`；“继续看”调用下一页，沿用它给出的全局连续序号。动作候选则先完成动作、节点、权限、重复操作等筛选，再把“最终可执行任务 ID 集合”交给 `task-table`。用户可见表格必须直接采用运行器返回的固定六列：序号、对象、名称、编号、当前节点、当前处理人。最终可执行数为 1–20 时完整展示全部行；超过 20 时只展示前 10 行并说明剩余数量。阈值只看最终可执行数，不能用最初命中数、合同总数或被拦截数替代。被拦截项另做原因汇总，不占可执行表格阈值。表格命令调用失败时停止并说明暂时无法生成可靠明细，不得靠模型手工补表。当前处理人必须取任务详情中该行对应节点的真实未办人员，不得用合同负责人、创建人或全流程待办人代替。任何筛选后的候选表都从 1 连续编号；序号绑定当前候选快照。运行器的 JSON 永远是内部数据，不直接粘贴给用户。
   - 待办总数超过 20 条时，在前 10 条表格之前使用 `task-list.distribution` 简要列出合同/合同组数量和节点分布；不能只报总数。分布来自完整合并后的待办集合，不得根据当前展示页自行推算。
10. 用户在抄送完成后追问“他看到了吗”“读了吗”时，直接对已锁定的业务任务重新执行 `task-detail`，读取 `detail.noticeSummary.records` 中与本次接收人匹配且时间最新的记录。只有 `readStatus=true` 才回答已读；否则回答未读或暂不能证明已读。不得通过阅读运行器源码、拼临时脚本或要求用户提供技术 ID 来查询。

## 不可绕过的约束

- 普通业务运行只能调用本节“运行入口”列出的公开命令。不得导入 `page_api.py` 内部函数、使用 `python -c` 拼接调用、自己构造 `curl`/HTTP 请求、读取 contract-cli 凭证文件、通过浏览器开发者工具重放接口，或修改运行器绕过确认和权限校验。源码检查只允许在用户明确要求维护或排障本 Skill 时进行，并且不得借此执行任何业务写入。
- 目标平台必须安装包含 `scripts/page_api.py` 的完整 Skill 目录；只复制 `SKILL.md` 不构成有效安装。首次业务调用先执行一次 `runtime-check`；CLI、Python、curl、User 登录或 Skill 脚本缺失时停止并说明缺失项，不退化成 Agent 自行调用接口。
- 只有 User 模式；操作者由当前登录态确定，不接受另一个操作者 ID。
- 只访问运行器内置的 test 标品页面接口白名单，不接受任意 URL 或路径。
- 审批通过、加签和转办只作用于当前用户真实承担的待办责任；抄送发起人固定为当前用户。
- 人员、合同、流程、任务、节点和类型 ID 只能来自用户明确提供、唯一上下文或页面查询结果；不得按名称猜 ID。
- 任务实例 ID、流程实例 ID、员工 ID、业务 ID、命令编码、接口路径、原始错误类型和请求标识只供内部执行与诊断；默认用户回复不得展示。
- 单条明确抄送以用户的直接指令作为执行授权；其他写操作先展示业务范围摘要。复合操作的一次确认绑定当时锁定的有序步骤、任务集合、数量、接收人和全部动作参数。
- 唯一单条抄送因附件等不支持项暂停后，用户明确说“不带附件继续”，该回复恢复的仍是同一目标和同一接收人的单条直接授权；重新核对通过后直接发送，不再机械确认，也不得只复述“尚未发送”。
- 多人抄送预览后，用户用“不要 B，只发给 A”等命令式表达把范围明确缩减为唯一当前审批和唯一接收人时，旧预览立即失效；重新预检后按单条明确抄送直接执行。用户说“先改成 A 看看”“只预览”等查看式表达时，只生成新预览，不发送。
- 确认依赖当前唯一有效的范围预览，不依赖用户复述固定话术；范围或参数变化后重新预览确认。
- 用户说“取消”“算了”“不做了”后，立即删除当前预览和相关授权，当前方案进入终止态。之后只有孤立的“确认”“可以”“执行吧”时，必须说明当前没有待执行操作；不得根据已取消的历史参数自动重查、重新生成预览或恢复方案。只有用户重新明确提出动作、目标和必要参数时，才开始一个新方案。
- 多任务或多动作操作按真实任务和步骤逐条执行，不宣称原子批量或原子复合；允许部分成功，失败项不自动重试、替换或回滚已完成动作。
- 批量结果不能只报成功、失败、未执行数量。至少逐条列出失败项的合同或合同组、节点和业务原因；未执行项也说明业务对象和停止原因。用户要求原始完整响应时不倾倒页面 JSON、请求集合或其他任务信息，只对其明确点名的失败项先给业务结论，再按需提供最少诊断字段及每个字段的排障用途。
- 批量执行被中断后，只有已保存写后核验结果的项目才能归入“已完成”或“已证明未执行”。尚未留下终态记录的项目一律是“待核验”，不能因为它排在中断点之后就说“剩余未处理”并直接续跑。先逐项复查，随后只对能够证明未执行的项目重新生成方案并确认；结果不确定的项目保持停止，避免重复写入。
- 超时或响应不确定时先重新查询任务状态；无法证明未执行时停止重复写入。
- 若当前会话已经收到“复查后仍无法确认”的页面结果，回复必须直接说“已复查但结果仍待核验”，不得再把“先复查”作为尚未完成的下一步。
- 当前运行器只执行 test 操作。测试环境可在必要时提示；未来生产运行时，正常查询、确认和结果中不得默认展示“生产环境”，仅在用户主动询问、授权诊断或环境异常时说明。
- 普通合同和合同组统一进入任务定位；合同组没有编号时用合同组名称、节点和时间消歧，不拿组内合同编号冒充合同组编号。
- 待办中的“当前处理人”覆盖审批、盖章、归档等人工节点：当前登录用户显示为“你”，多人节点展示实际姓名；读取失败时明确显示“暂未取得”，不得根据任务负责人猜测。
- 用户说“审批”或“历史审批”时，只在真实审批节点中选择；用户明确指定提交、归档等其他人工节点时，保留真实节点名称，并且仅在页面实时开放动作时处理，不能把它们统称为审批节点。
- 人员重名但页面没有部门、邮箱、工号等可用区分信息时，直接说明当前数据无法安全区分并停止；不要反复索取页面无法验证的信息，也不展示员工 ID 让用户选择。当前人员搜索不会返回可供业务用户判断的离职档案：搜不到只说“未找到”，搜到唯一当前可选人员就按唯一结果继续，不能声称识别了离职或再入职记录。
- 上述“无可用区分信息”是人员解析的硬停止条件：一旦页面已经证明同名候选的部门、邮箱、工号均为空或相同，不再继续收集合同、加签方式、原因等后续参数，也不能让用户再提供这些候选记录当前并未维护的邮箱或工号。只允许提示“请管理员补全人员目录后重试”或“改用另一位可唯一检索的人员”。用户要求“随便选一个”时明确拒绝并结束，不继续形成执行方案、不写入。
- “预览”只在已经形成可执行方案、需要向用户展示范围并确认，或用户明确要求查看方案时出现在用户回复中。人员未找到、人员无法区分、目标不唯一、权限不足等在成案前发生的拦截，只说明没有执行的业务动作、具体原因和下一步；不得主动汇报“未生成预览”“零预览”“没有有效预览”等内部过程状态。取消后的孤立确认统一回答“当前没有待执行操作”，不要求用户理解预览状态。
- 所有用户可见内容都直接说明业务事实和下一步，包括处理中、重试、预览、拦截和结果。若宿主运行环境要求透明说明正在使用的 Skill，可在首次过程提示中用一句自然话说明一次；此后不要反复提“Skill”“技能”“调用某技能”“按某技能流程”，也不得引用“Skill 规则”“技能要求”“内部安全规则”等实现口径作为业务理由。用户主动询问所用能力、技术实现或正在进行 Skill 测评时，可以进一步说明 Skill 名称。例如首次可说“我会使用合同审批动作能力核对人员和审批范围；加签前会把方案列给你确认”，后续直接说业务进展。任何轮次都不要用“我会按合同审批动作规范处理”“按合同转办流程处理”“我会按‘智书合同审批加签’流程处理”“按规则核对”或任何“我会按 XX 流程处理”的过程套话；直接说“我先核对这份合同、当前审批节点和接收人；确认后再执行”“已取消，不会执行”即可。面向普通业务用户不得把内部阶段称为“预检”；改用“已核对”“准备执行”或“方案如下”。
- 普通业务查询的过程提示只说“我查一下你的合同审批待办”等业务动作；不得说“先读取操作规范/Skill 文件/接口契约”。正常查询结果不附“反查点位”、测试建议或实现说明；只有用户明确处于测评、验收或排障任务中时，才把这些内容写入测评报告，而不是混进被测业务回复。
- 合同名称查询同时命中一个唯一完全匹配项和若干前缀、后缀或“副本”包含项时，优先使用完全匹配项；不得按更新时间把包含项当成目标。只有多个完全匹配项时才进入编号、节点或时间消歧。
- 任何经过动作、节点、名称或类型筛选后展示给用户的候选列表，都必须按展示顺序从 1 连续编号；不得沿用原始任务集合中的 3、4、7 等断号。用户说“第 N 条”时，必须绑定这次展示的第 N 行及其锁定快照。
- 所有待办、候选和批量动作明细都固定使用六列“序号／对象／名称／编号／当前节点／当前处理人”。普通待办由 `task-list` 生成，动作候选由 `task-table` 生成。最终可执行数不超过 20 时不得改成“示例”、省略剩余行或减少字段；超过 20 时首批展示前 10 行。发送回复前核对 `presentation.columns`、`candidateCount`、`displayedCount` 和 `remainingCount`，不符合时不得请求用户确认。
- “给这个合同加签/转办/抄送”且没有指定其他节点时，候选范围先按真实审批节点过滤，再编号展示；不得为凑齐原始待办而混入盖章、归档等无关节点。
- 加签人是否可编辑合同属于条件业务项：节点已经固定为可编辑或只读时直接使用页面配置，不向用户展示或追问；只有选定任务的页面配置明确要求发起人选择时，才追问“加签后允许对方编辑合同，还是只能查看并审批？”，不得使用“属性可编辑配置”等技术措辞。
- 加签候选属于“可执行选择”，不是所有审批待办。已知加签人已经是当前节点处理人的任务必须在编号前排除；不得展示在候选表中再用备注说明不能选。

## 能力边界

- 用户给出的业务名称只是合同或合同组的名称内容；名称中出现“飞书”“审批”“任务”等词，不构成切换到飞书原生审批或其他产品能力的依据。只有用户明确表达要处理飞书原生审批实例、飞书审批中心或给出飞书审批实例线索时，才离开本 Skill。
- “把〈业务名称〉的审批抄送/转办/加签给某人”属于名称型合同请求：必须先把完整业务名称送入合同任务查询。即使用户没有重复说“合同”二字，也不能仅凭动作词“审批、抄送、转办、加签”改走飞书原生审批。合同侧查无目标时，应向用户说明未找到并追问是否指飞书原生审批；不得自动发起飞书授权。
- 审批矩阵、审批路由规则或协商自动邀请配置：使用 `contract-cli-rule`。
- 飞书原生审批待办、实例或审批定义：使用 `lark-approval`。
- 审批记录、审批耗时、慢节点、趋势或 SLA：使用审批时效分析 Skill。
- 审批通过仅支持页面实时开放 `agree` 的当前真实审批节点，且节点不能要求同时编辑合同内容；拒绝、撤回、催办、终止流程或修改流程定义仍不支持，不用其他动作替代。
- 混合指令中的不支持动作必须在第一条用户可见回复中拦截。此约束覆盖过程提示、计划说明和最终答复；后续纠正不能抵消前面已经造成的能力误导。

## 评审与回归

用户要求评审、联调、回归或实机测试时，先读 [测评执行手册](tests/test-plan.md)，再按 [端到端会话集](tests/journey-cases.yaml) 验证完整用户任务，并用 [原子测评集](tests/scenario-cases.yaml) 补充局部规则和接口边界；普通业务调用不加载整套测评集。

- `dialogue`：只验证判断、追问、确认和用户可见输出，不调用真实接口。
- `readonly`：调用真实查询、定位和预检接口，不写数据。
- `live_write`：使用独立的一次性测试样本真实写入，并保存页面业务响应和写后复查证据。
- 用户明确要求“实际测试”时，不得用推演替代 `live_write`；样本或接收人不足时，明确列出需要补建的样本。
- 测评集本身不构成写入授权。每次 `live_write` 仍需由测试执行人明确选定本轮案例和测试数据，并遵守本 Skill 的范围预览与确认规则。
- 加签和转办会消耗或改变待办，不能在同一任务上连续复用多个写案例。批量、并发变化和部分成功要使用专门夹具。
- 每次回归至少运行包校验、无网络单元测试、P0 `dialogue/readonly`；发版前在具备样本时运行全部 P0 `live_write`。
- 测评结果必须标明数据集版本、协议版本、实际执行层级和缺失证据；“案例文件校验通过”不得表述为“所有案例执行通过”。
- 端到端结果必须来自同一会话连续执行到明确终态，并保留每轮用户原话、助手回复和工具调用；单轮原子结果、拼接对话或只写“已有上一轮上下文”的前置条件不能作为完整交互通过证据。
