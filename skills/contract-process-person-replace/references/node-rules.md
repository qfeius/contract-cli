# 节点查找与人员多选替换

## 读取位置

定义 VO 的 `processDefinitionJson` 是字符串。其内层根对象的 `node_models` 数组保存流程节点；保持数组顺序及全部节点，不把界面显示名当节点标识。

仅将以下节点列为本业务的人员替换候选：

| 字段 | 判据 |
|---|---|
| `node_type` | 严格等于 `USER_TASK` |
| `process_type` | `approve`=审批、`seal`=盖章、`archive`=归档 |
| `node_id` | 同一份定义内唯一、非空的真实节点标识；作为不透明字符串保留 |
| 配置根 | `component_props.clm_form.approver` |

`node_name` 用于展示；它是字符串时原样显示，是语言对象时中文会话优先已有 `zh` 文本，否则使用实际可用语言文本并说明。缺少时显示节点名未返回，不猜节点身份。只读取与本次人员检索和节点定位有关的数据，不额外检查流程或节点的其他设置。人员名单、节点标识或图确实无法读取、解析或识别时，记录受影响的查询范围；已读人员配置没有目标人员，则判为未匹配。

检查 `node_models` 中所有符合条件的节点，包括不同条件分支。不做字符串全文替换，不按姓名、节点名称或表达式中的子串匹配人员。

## 直接指定与动态规则

| 当前规则 | 处理 |
|---|---|
| `personnel_type_code=0` | `employee_ids` 是内部人员 ID 的字符串数组，按精确 ID 命中 |
| `personnel_type_code=13` | 沿 `approval_rule_list` 数组递归，只在 code 0 叶子匹配；保存每层数组位置及原规则值 |
| 其他 code | 动态、角色、表单、上级、部门、矩阵等规则不改；不把其缓存或残留人员字段当作直接指定 |

原生 DTO 同时支持三组字段名：`personnel_type_code/personnelTypeCode`、`employee_ids/employeeIds`、`approval_rule_list/approvalRuleList`。读取时检查实际返回的原字段，逐层沿 code 13 的实际规则列表继续，不对整份图做命名转换；记录命中路径时保留真实字段名。两种字段同时返回且值冲突时，不能猜哪一个生效。

非 0 规则即使残留 `employee_ids`，也不能据此认作直接指定。动态规则只说明其配置存在，不承诺目标人实际会被选中，不修改角色成员、部门负责人或矩阵。

本次不替换 `notice.receiver.employee_ids`（抄送）、`when_blank.employee_ids`（兜底）、`approval_terminal_info.terminal_assign_persons`（逐级终点）或其他同名字段。它们与三类节点的直接审批人语义不同。

人员必须用 `EmployeeVO.employeeId`。`userId/openId/accountId/larkId/memberCode`、显示姓名、缓存标签都不是同一标识。记录中的 `employee_options` 只用于显示缓存，不能据其 label/name 判断人员命中。

## 查询匹配与不匹配

仅在实际读取到的直接人员配置中按目标 ID 判断。直接名单不含目标，或所有可读的 code 13 规则中没有直接指定目标，就是未匹配。审批人没有设置、人员名单没有填写或为空，且没有未读或无法识别的人员配置时，同样是未匹配，不进入结果，不另作流程配置提示。

缺少选人类型但已读人员配置没有目标 ID，也按未匹配处理。不能因为节点状态、空表达式或缺少其他设置，推测目标人员可能存在，或把这个节点列成匹配待确认。查询阶段不校验其他设置，不评价流程是否可用，也不生成流程检查清单。

真实的接口失败、图无法解析、人员名单或标识无法识别、别名冲突等，只有影响本次匹配时才记录为“本次人员查询未成功”的具体范围；不能擅自当作无匹配，也不据此评价流程好坏。不能确认语义的规则不擅自认作直接指定或进行替换。其他人员的姓名/部门回读失败，不改变已明确的目标 ID 匹配。

不为未匹配节点补人员、补默认类型或改其他设置。相同流程中的其他匹配节点继续正常列出。后续只有在用户选中并确认实际替换批次后，才执行原有编辑、保存、发布与结果回查；原生接口在这些动作中返回失败时按实际操作结果处理，不提前将查询扩成流程检查。

## 一行与多处命中

扫描结果以 `(formId,node_id)` 为一行。同一节点多个直接规则叶子命中旧人时，一行展示，并保留全部命中路径和出现位置；选择此行意味着处理这些命中位置，不能只替换第一处。

“审批人”列展示该节点的完整人员多选配置；混合规则按组和原顺序展示，区分直接人员与动态规则，标出旧人员。同名人员附部门，人员元数据回读不全时保留未知项数量/状态，不猜名字。旧人身份未核实的节点不能进入写批次。

同名节点、不同分支节点保持独立；相同节点 ID 出现在另一个流程或版本时不混用编号。

## 替换规则

只修改用户选中行对应的 code 0 叶子：

1. 新 ID 与旧 ID 相同：无需修改，该行不触发 edit/save/publish。
2. 叶子的 `employee_ids` 没有旧 ID：不增加新人，标明源与当前配置不一致或无需替换。
3. 新 ID 尚未在同一列表：在第一个旧 ID 的位置放入新 ID，移除其余旧 ID 命中，保证本次目标新人员在这个列表只保留一次。
4. 新 ID 已在同一列表：保留其第一个原有位置，移除全部旧 ID 和这个目标新 ID 的其他重复位置。其他人员的顺序、出现次数和规则不清洗、不改写。预览说明人员数量变化。
5. 不跨 `approval_rule_list` 合并、重排、删除规则组；新人员已在其他组时原组结构保持，并在预览说明跨组重复的影响，不以运行时去重推导可以删组。

节点的 `task_mode`、组件内对应审批方式、审批人为本人策略、条件、分支、顺序、权限、自选配置、超时、抄送、兜底及全局配置保留。`serial`、`parallel`、`exclusive` 各自的语义不能因换人改写；多选去重可能减少会签人数、串行参与者或或签候选，必须回显。

## 显示缓存与执行字段

`employee_options` 存在且是有 `value` 的选项数组时，按精确内部 ID 同步目标人员缓存：保留其他选项，已有新人员选项只保留第一个；删除被替换的旧选项；无新选项时只补普通选项 `value=新employeeId`、`label=新displayName或name`。其他人员缓存不额外去重。不要复制前端 React 展示对象、凭据或无关个人信息。缓存缺失时允许保持缺失，由页面按真实 employee_ids 回读；无法辨识的既有缓存结构不猜写，保留并报告显示缓存未核实，不把它当执行身份。

对每个变更节点，按接口协议把修改后的**完整 approver 根对象**提交原生表达式生成能力，成功的非空 `data` 写入该节点 `approvers_bo`。混合选人不能只给一个叶子，不能手拼 `user:`、`PROCESS_NODE_CONFIG` 或其他表达式。

原 snake_case approver 的必要字段有后端别名支持，可直接提交克隆副本，不做整份流程的 camel/snake 转换。表达式 API 忽略未知字段且只返回字符串；完整未知配置仍保留于本地流程 JSON 和最终保存请求，不能声称表达式接口帮忙透传。动态配置内部的别名并非完整通用协议，本任务不改它，也不依赖它生成直接指定人员规则。

修改后 code 0 或 code 13 根不是共享挂起节点。保持其 `is_suspend=false`、`suspend_call_api_code` 为空与原表达式一致；若原字段已不一致，先在预览中列为额外执行字段差异，不静默把别的动态节点改成直接人员。未变更节点的表达式、抄送执行字段不重算。

## 保存与发布回读的不变量

以完整编辑目标快照为基线，确认：同一 node_id 仍属原节点类型/流程类型；节点数及顺序、边、条件、审批方式和所有非目标配置保持；选中叶子只发生预期 ID 多选变化；目标缓存及 `approvers_bo` 同步，其他节点未被改写。

`nodeConfigMap` 不保存直接指定 employee_ids，需完整保留其字段权限、自选审批和排序配置，不为换人重新生成。不能把修改请求里的节点数组或 `nodeCount` 等自造字段加到保存 DTO 中。

比较 JSON 的所属对象、值和类型，允许合法转义等文本表示差异，不要求字节一致。API 规范化导致的额外业务变化不能自动忽略，按主流程停止该对象的后续发布并报告实际保存状态。
