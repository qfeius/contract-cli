# 范围、结果列表与版本处理

## 查询范围

本业务限定后台 **系统管理 → 合同配置 → 合同流程管理** 的全部业务分类：申请、变更、终止、合同组申请、修改表单、合同作废。读取已发布版本和后台列表最新配置；不扩展到履约提醒中单独关联的流程、续签旧入口、批量申请或全部历史版本。

按 API 协议显式逐类型读取，不依赖省略 type 的默认结果。变更两个实际编码均查询，保留既有旧类型配置；功能开关用于说明当前页面配置，不因开关关闭就把已返回的流程默删。查询两种 published 视图，同 formId 关键字段一致时合并；相同 ID 内容冲突时重新核对，不取最后一条覆盖。

列表的 `published=false` 不是“仅未发布”：它返回按 changed 条件保留的最新可展示配置，可能仍是已发布版本，也不保证列出尚无改动的编辑副本。`published=true` 返回当前已发布版本。两者都不是历史全集；某次查不到模块不能外推历史不存在。

每份真实定义只 GET 一次取得扫描快照，另有需要时再回查。空流程图没有三类节点；已读人员配置没有目标人员，包括尚未配置审批人的节点，按节点规则判为未匹配，不列出。保留各类型/版本查询成功、未成功的范围及命中数，查询阶段不额外检查其他流程设置。显示分批时保留所有编号映射并明确总数，不能以宿主截断当查询结束。

## 版本与同逻辑流程

先按 `formId` 精确去重。同一租户、同一 businessTypeCode 下，非空规范 `processDefinitionKey` 形如 `clm_<当前类型码>_<正十进制字符>` 时，可把相同完整 key 的一条已发布和一条草稿作为同逻辑流程候选。key 保持不透明字符串，不解析或计算其中数字。

`clm_1` 等旧共享格式、缺失 key、类型前缀不符或同组出现多个已发布/多个草稿时，不自动归并；继续分开列示并标明版本关系未核实。不能按同名、同范围或 formUuid 合并，复制流程可能共享 uuid。版本关系未核实影响一次保存发布计划时，停止该流程的写入并保留具体缺口。

分组只用于清单和防重复处理，后续写目标始终用 edit 实际返回的 formId。`previousId` 可能是大数值，不能为了判断血缘而把它经过 Number 转字符串；缺少可靠关联时不猜。

## 列表格式

默认按后台流程分类分组展示，每行同时必显“流程分类”，不能仅在同名或双版本时补充。分类与顺序只按实际 `businessTypeCode` 映射，唯一维护在本节：

| 展示顺序 | 流程分类 | 实际业务类型编码 |
|---|---|---|
| 1 | 合同申请 | 0 |
| 2 | 合同变更 | 2、16 |
| 3 | 合同终止 | 3 |
| 4 | 合同组申请 | 10 |
| 5 | 修改合同表单 | 12 |
| 6 | 合同作废 | 15 |

这是后台流程的业务分类，与适用范围中的一级/二级合同类别不同；不从流程名称或 `categoryScope/categoryScopeName` 猜分类。2 和 16 只在展示上归入“合同变更”，保留每行真实编码、对象和版本关系，不跨编码归并流程或修改请求。出现未知、缺失或冲突编码时列为“分类待核实”，保留原始值及受影响范围，不塞入相近类别。

同一分类内将同一流程的已发布版与草稿邻近列出并标清版本；同名流程仍按真实对象区分。全表使用连续、唯一的 1–N 编号，分类、版本或分页切换不从 1 重新开始。当前清单已经冻结时，补充分类只增加展示信息，保持原编号与对象/节点/规则映射；需要重排或重新编号时明确生成新清单，不能沿用旧编号执行。

汇总按上述六类说明匹配节点数及流程版本数。某类已查询成功且无命中时写“0 个匹配节点”；审批人没有设置或名单没有目标人员，不产生额外提示或匹配待核范围。真正读取失败、人员匹配数据无法识别或扫描未完成时，才说明“已找到 X 个，另有范围未查询成功”，不能以 0 代替未查成功。未知分类只保留本次人员检索所需的分类说明。

每个分组表至少包含以下列：

| 列 | 内容 |
|---|---|
| 序号 | 本次全表连续唯一的 1–N，冻结到流程分类、真实类型、版本、node_id 和命中规则路径 |
| 流程分类 | 本节映射后的真实业务分类，每行必显 |
| 审批流名称 | 原真实名称，标清已发布版/草稿版；不把分类拼进名称来代替独立分类列 |
| 节点名称 | 原名，附审批/盖章/归档类型；同名分支保留区别 |
| 审批人 | 该节点完整配置，旧人突出，同名人员附部门，动态规则按组显示 |
| 发布状态 | 已发布/未发布/状态未核实，并标注已有草稿 |

人员多选直接这样表述：“当前多选：张三、李四；替换后：王五、李四”。旧人替换成已选新人时显示“当前：张三、王五；替换后：王五，人数 2→1”，不要求用户理解去重算法。

结果中当前已发布版和草稿版都命中时，分别标清版本，不隐瞒差异；执行前再按逻辑流程归并。动态节点提示只说明存在非本次范围的规则，不声称已找出它实际会命中的人员。

同名或状态异常的人员候选只给本任务需要的姓名、部门、状态、序号；不把内部 ID、电话、邮箱或凭据倾倒给用户。

## 查询输出范围

结果表只列实际匹配目标人员的流程节点。没有配置该人员的节点不显示，不另列这些流程的设置问题、状态评价或修复建议，不输出流程好坏或设置是否齐全的检查报告。

同一流程中的其他匹配节点正常列出。发布状态、已有草稿、完整人员多选名单及动态规则仍按本 Skill 的既定要求展示，用于识别匹配对象与后续替换范围；它们不构成对流程设置的评价。只有本次人员查询确实未成功的范围需要如实说明。

## 全部与编号选择

“全部修改”指这份已完整扫描且冻结清单的全部匹配行，不能扩大到新扫描结果、隐藏历史、其他人员或本批未读取成功的流程。指定编号可以多选，去重后按原映射处理；未知/过期编号须澄清，不能跳过后继续当全部成功。

查询不完整时，先补齐失败范围，或让用户明确只处理已列出的部分；不能把没有限定的“全部修改”自动解释为部分成功结果。

同一节点多个命中规则按一行全部处理。多个版本/节点属于同逻辑流程时，合并为该流程的一次保存发布计划，保留选择来源，不分别 edit/publish 两次。

当前草稿是写入基线，不把已发布旧快照覆盖上去。选中已发布版的节点在草稿中缺失、类型/规则位置不同或旧人不再存在时，在确认预览里说明，不把同名节点当替代。草稿已完成相同人员替换的，不能虚报本次修改；仅发布现有草稿是否纳入本批须让用户看清并确认。

## 一次具体确认

摘要显示：旧人员、新人员、所选编号、流程分类、节点变化、实际流程数、各流程当前发布状态、已有草稿及本次保存发布目标。已有草稿不默认跳过；用户根据清单确认处理范围。

对将发布的已有草稿，明确一句：“其中已有的未发布修改会一起生效。”不将该效果隐藏成仅替换人员，也不要求每个节点逐一重复确认。已在本轮完整确认同一批次时直接沿用；人员、身份、版本、选择或配置变化影响方案时才补充相应确认。

只读选择阶段不调用 edit。具体保存发布批次确认后才能初始化编辑；若 edit 发现列表未显示的既有草稿或额外配置差异，停止该对象后续动作并说明新事实，不能自动接受未在确认范围内的变动。其他独立流程可以继续。

## 完成和部分结果

完成必须区分：查询完成、人员配置已保存、流程发布已核验、存在失败/未知。结果沿用流程分类与已冻结编号，不能因执行状态分组而隐藏分类。默认逐流程报告，必要时展开对应节点：

- 已发布且回查通过：发布目标及节点替换都已确认。
- 已保存未发布：替换保存通过，发布失败、未执行或校验未通过。
- 已生成/复用草稿：edit 完成，后续未完成；保留实际新 ID。
- 无需替换：旧新相同，或已确认的目标配置已经一致；不假称本次写入成功。
- 未执行/失败/结果未知：指出发生阶段、原因及可继续的只读核查。

批次部分成功不自动回滚其他流程，不把单份成功外推整批。原生发布不会自动把所有在途合同换人；模板绑定更新异步，也不在本批发布回查中宣称逐个完成。

需页面接续时，Origin 只用本轮已核实系统站点或用户确认的当前环境登录 URL，不能从 API 域名推导。0/2/3/10/16 使用 `/admin/contract-config/workflow?formId=实际ID`，12/15 使用 `/admin/contract-config/workflow-process-only?formId=实际ID`。先使用目标实际类型与 ID 生成标准文字链接。
