# 合同流程节点人员替换

用户提供旧人员，找到后台“合同流程管理”中配置了该人员的审批、盖章、归档节点。结果按流程分类分组，分类为每行必显字段；全表连续编号，用户可选择全部或部分编号，并指定一个新人员。提交前展示人员多选列表的前后变化、发布状态及已有草稿；取得具体批次确认后，按流程保存并发布，再回查结果。

本包只含 Markdown 和宿主声明元数据。执行复用当前 `contract-cli` 的现有命令与宿主普通文件能力；不增加任何语言的脚本、解析器、转换器、测试程序、外部依赖或自编执行代码。制作或安装本 Skill 不授权真实修改；查询不触发编辑初始化。

## 1. 固定执行上下文

按[运行方式](references/runtime.md)核实当前 CLI、USER、实际环境及租户，复用本轮可靠上下文。先只读查询当前本人功能权限，确认实际包含后台 `admin`，再枚举流程。查询、人员定位、选中行、编辑、保存、发布和回查保持同一上下文。只有后台权限允许读取的流程才可扫描，不能切 APP 或其他身份补权限。

本业务的范围、双版本查询、列表编号与确认规则维护在[交互与版本处理](references/interactions.md)。节点结构、直接指定人员及多选替换规则维护在[节点规则](references/node-rules.md)。实际请求、字段来源与结果判据维护在[接口协议](references/api.md)。

## 2. 定位旧人员并扫描

取得用户提供的旧人员业务信息。复用已确认的准确身份；只有姓名或同名不明确时，按接口协议显示姓名、部门和状态供选择，不默认取第一条，不让用户寻找内部 ID。

先按接口协议读取本人 `/permission/function/list` 并核实 `admin`，再成功取得后台流程列表，之后进行本业务所需的其他人员查询。角色页面中“合同流程管理”及发起补充/终止/修改表单/创建子合同的操作项不代替后台 `admin`。按交互规则逐分类读取当前已发布版本与列表最新配置，按真实 ID 去重，只读 GET 定义。各分支中的三类节点都检查，按节点规则匹配内部人员 ID，不对整份 JSON 做姓名或 ID 子串替换。

人员已离职或姓名搜索找不到时，可以从已获准流程中的直接指定人员 ID 收集候选，复用原人员批量回读能力确认；不能把正常人员搜索为空说成不存在历史配置。无法确认旧身份时保留待确认，不猜测或自动选择。

查询只回答目标人员配置在哪些审批、盖章、归档节点。按节点规则实际命中才进入结果；已读人员配置中没有目标人员，就是未匹配，不显示该节点。不在查询阶段检查或评价流程设置是否齐全、是否有效、能否发布，也不另列无匹配流程的配置问题或要求用户修复。

只有部分分类、定义或匹配所需数据确实无法读取、解析或识别时，才说明本次哪些范围未查询成功，保留其余结果；不能把无法读取当作没有配置。其他人员姓名回读不全时仅保留名单中相应人员的资料未返回说明，不影响已明确的目标 ID 匹配。所声明范围均已查询成功且没有命中时，直接说明“未找到配置该人员的审批、盖章或归档节点”。

## 3. 输出结果并接收选择

按交互规则分组并输出：**序号、流程分类、审批流名称、节点名称、审批人、发布状态**。流程分类始终显示，采用交互规则中唯一维护的映射、顺序和完整性说明，不只在流程同名时补充。节点名称旁标明审批/盖章/归档；同名流程和两个版本显示版本说明。审批人展示完整的多选配置，标明命中的旧人员；动态规则显示规则含义，不冒充已解析的实际人员。

保留全表唯一编号到流程分类、真实业务类型编码、当前流程 ID、节点 ID、规则位置、版本及原配置的完整映射。分组不重置编号；为当前清单补分类时保留已冻结编号。用户说“全部修改”仅指当前已完整查询并冻结的结果；指定编号只能使用当前映射。新人员提前给出则沿用，没有给出才询问。

新人员按接口协议唯一定位并核实正常可选状态。旧、新人员相同则说明无需替换，不编辑、不保存、不发布。只替换目标旧人员，保留其他多选人员与审批规则；新人员已在同一人员列表中时只保留一次，并显示人数变化。

## 4. 冻结保存并发布的批次

逐行展示流程分类及旧人到新人的变化，按同逻辑流程归并为一次保存发布。列表标清已发布、未发布、已有草稿和未能核实的状态；已有草稿不自动跳过，由用户看清状态后选择。摘要明确：**发布现有草稿会连同其中已有修改一起生效**。

确认绑定当前身份、旧/新人员、所选行及实际待处理版本。只完成一次具体批次确认；已完整确认且条件未变不重复询问。查询授权、一般修改意向或单独提供新人员不代替具体保存发布确认。

如同一流程两个版本有匹配，或选中已发布节点与现有草稿不一致，按交互规则处理映射和冲突，不分别发布两次，不把旧版本整份配置覆盖到草稿。

## 5. 逐流程编辑、替换、保存

对已确认批次逐流程执行，成功与失败分开记录，未发送的继续保留原状态。

1. 只读重读源及已知草稿，与冻结的人员、节点、版本和可写配置比较。漂移影响方案时停止该流程，保留差异供确认；不静默扩大修改范围。
2. 按接口协议调用一次原生 edit。该调用会创建或复用并规范化草稿，属于写动作。以实际返回的新 `formId` 为后续目标，重新定位所选节点及规则，不根据名称猜新节点。
3. 只按节点规则修改已确认的直接人员列表和必要的显示缓存，保持其他人员、组结构、模式、条件及配置。用原生表达式接口重新生成变更节点的完整审批人表达式，不能自己拼表达式。
4. 按接口字段表从完整编辑快照组装全量保存请求。不能只发送流程 JSON，也不能把原返回整个 VO 不加区分地当 DTO。检查实际请求大小符合 CLI 限制；超限或必要字段无法保真时停止该对象，不删字段来凑请求。
5. 保存前重读目标草稿；一致后仅发送一次 update。GET 回查目标人员及保存不变量，确认通过后才进入发布。

edit、保存过程中原系统可能进行模块合并或配置规范化。发现超出已确认人员替换的业务变化时，保留实际阶段与差异，不在未明确其影响时继续发布，也不自动删除草稿或回滚其他修改。

## 6. 发布与回查

本 Skill 的完成动作包含发布。保存回查通过后，按接口协议再次核对目标快照，发送一次原生 publish，并检查业务结果及真实目标状态。不能把保存成功、发布请求已返回或 `result=true` 单独当作已生效。

发布完成须满足：实际目标已发布、选中节点旧人已按预期替换、其他人员和规则保持、当前已发布列表中的版本与目标一致。按接口协议处理校验错误、多语言提示和异步模板更新边界。未明确证据不承诺所有存量合同、模板或在途流程立即迁移。

发布失败保留“已保存未发布”等实际状态；任一写请求超时、断连或响应未知时先只读回查，不自动重试、不重放整批。不要声称跨流程原子成功。

## 7. 交付结果

返回逐流程/逐节点的执行结果：已发布且核验通过、已保存未发布、仅生成草稿、无需替换、未执行、失败或结果未知。给出实际处理数量、失败原因及未完成范围，保留用户可继续处理的输入和对象。

用户要求页面接续时，使用已核实环境的原生编辑链接及完整导航，不从 API 域名猜页面域名。缺少能力时说明受影响节点、当前步骤、最小缺口与验收条件，继续其他独立工作；不改 CLI、权限、后端或服务来补齐本 Skill。
