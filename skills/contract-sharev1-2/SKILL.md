# contract-sharev1-2

完成内部分享、记录查询、取消或调整期限。每次分享产生独立授权；重复分享新增记录，上游取消或到期不自动撤销下游授权。

## 确认任务与当前能力

- 沿用用户已说明的动作、合同、接收人和期限；查询、写入及回查保持同一环境、租户和当前组织用户。环境不明确时先确认，不默认生产或测试。
- 优先复用宿主已授权的查询与分享能力。使用页面接口前读取[接口与通道](references/api.md)，核对真实 CLI 帮助或 MCP schema；缺少调用器、登录或路由时，只停止依赖该能力的动作。不从合同链接复制登录态，不构造凭证或可信身份头，不换身份或通道绕过业务拒绝。
- 按[接口准入](references/api.md#接口准入与停止条件)逐动作核对对象、权限、状态和参数。正常创建、批量及取消满足对应条件后执行；部门限制或关联范围不明确时，按具体分支停止。审查依据与验证边界见[准入说明](references/api.md#准入说明与验证边界)。

## 定位合同、人员和记录

1. 按名称或编号，复用当前用户可见合同的已核实搜索能力；沿用本轮可靠搜索结果。多条候选时用名称、编号等业务信息消歧，不自动选首条。没有搜索能力时，可请用户提供详情链接，不让用户查内部 ID。
2. 对详情链接，仅提取合同候选标识，随后读取当前用户授权范围内的真实合同详情。以详情响应的合同 ID、业务类型和状态为准，不能直接把 URL 数字当作已验证对象。保留名称、编号、创建员工和可靠关联范围；同组合同不自动等同于同一授权对象。
3. 创建分享时，读取[人员解析协议](references/api.md#人员解析)解析用户指定的本租户员工，与详情中的创建员工及当前用户信息衔接。名称重复时展示必要的部门或邮箱供用户选择；没有命中只说明本次查询无匹配，不声明此人不存在。单次不超过 50 个不同接收人，不静默拆分超限请求。
4. 查询或取消时，从当前合同的分享记录中取真实记录 ID、资源 ID、分享人与接收人、有效时间和启用标志。取消或改期须明确对应记录；同人多条记录不能默认全选。

创建分享或调整期限前，必须读取[业务规则](references/business-rules.md)中的分享效果、权限、状态、有效期及关联影响；查询或取消时读取其中的记录管理规则。不要通过分享来验证合同是否可访问。

## 分享合同

1. 读取当前企业分享配置、目标合同详情和“是否可分享”结果；按业务规则核对角色范围、权限来源、真实状态和接收人。权限结果未知、服务返回异常或配置缺失时，不能当作默认放行。
2. 确定本次实际授权的全部合同与版本。补充协议、终止合同、存在后续版本等情况可能展开为同组多份合同；无法确定展开范围或逐对象权限时停止，说明缺少授权范围解析能力，不能先分享后看结果。
3. 按当前配置计算期限，将相对时间转换为明确日期；说明所用业务时区。期限控制启用时，显式发送 hasExpiration=true，截止日期必填且不得超过本次分享起算的配置上限；配置上限或日期解析时区无法核实时停止。用户未提供期限时询问截止日期，或提出不超过配置上限的日期供其确认，不默认永久。截止时刻已过去时，说明无法产生当前有效的访问授权并澄清用户意图，不无提示提交。未启用时，现有正常流程是无到期授权；若用户要求有限期限但当前能力不支持，说明差异并等待用户选择，不能静默改成永久。
4. 写前展示可审阅清单：合同名称与编号、实际关联范围、接收人、截止日期及时间或“无到期时间”、授权效果和自动通知／拉群影响。明确分享可带来评论、普通下载与打印等现有详情能力，不承诺纯只读或不可下载。取得覆盖这些具体对象及影响的明确确认；用户此前已完整授权的内容不重复询问。
5. 提交前重新核对当前权限、状态、配置和实际关联范围，不能依赖上一次合同或上一位接收人的检查结果；与确认清单发生实质变化时，重新取得覆盖变化的确认，不以旧确认继续。发送一次获准请求，记录返回的分享记录 ID。按[创建与回查协议](references/api.md#创建分享与回查)核对全部预期资源和接收人，区分成功、部分成功、业务失败和结果未知。顶层业务成功或 `shareable` 允许不代表每个接收人都完成了分享。

多个用户指定合同的批量目标保留原范围。对每份合同分别读取真实详情、权限预检查、状态和完整关联范围；对每个接收人完成身份核对。只有所有预期资源均允许分享、期限合法且未命中其他限制时，才使用同一创建入口提交多资源请求，最多 100 个请求资源、50 个不同接收人。不得用一份合同的权限代表整个批次。按实际业务类型与合同 ID 组成资源键，消除本次意外重复选择并向用户说明；关联展开有重叠而无法避免重复授权时先澄清。不能把名称相同当成同一合同，也不删除历史分享记录。用户有意重复创建独立授权时，明确数量并取得对应授权后单独制定计划。

有对象被拒、权限未知、关联范围不完整或超过请求上限时，写入前停止原批次，列出逐项原因；只有用户明确接受缩小范围或分批计划后，才重新检查并执行新计划，不静默过滤或拆分规避。提交后按每份实际资源与接收人的组合回查；部分成功保留成功记录，不重放整个批次。批量通知与单份拉群行为可能不同，按实际请求形态说明影响。

## 查询与取消分享记录

查询需要合同管理页面权限和对应合同访问权限；范围是该合同记录，不限于本人发出的记录。按[记录协议](references/api.md#分享记录)展示分享人、接收人、期限及可确认状态。无记录时报告“该合同当前查询未返回分享记录”；不要据此断言从未分享。

取消前，重新验证目标合同访问权限，并从该合同的记录接口读取用户指定的记录。核对记录 ID、businessId 与目标合同、业务类型、接收人及当前租户上下文一致；不能仅接受用户、链接或旧缓存给出的记录 ID。字段缺失、记录未返回、对象不匹配或同人多记录未消歧时停止。展示具体记录、接收人与影响并取得授权后，按取消协议逐条执行；不限定必须是原分享人。正常匹配的记录不因缺少后端整体修复证明一律禁止，但不能据此声称服务端已防住错配请求。

详情入口每次取消一条记录。完成后按[取消与回查协议](references/api.md#取消与回查)验证该条记录的结果。表述为“对应分享授权已取消”，不声称接收人失去全部访问权，也不自动取消其他有效记录或下游转分享。不改用管理后台按日志撤销的入口兜底。

## 调整期限

已有记录不能直接改期限。先解析旧记录和新期限，完成新分享所需的全部准入、对象及配置检查，再展示“取消旧记录＋新增分享”两步计划并确认。任一步能力受阻时，不先取消旧记录。

还须确认取消旧记录后，当前操作者仍有读取、创建和回查所需的权限。若其权限仅来自即将取消的记录，或无法核实取消后的有效权限来源，不开始改期，说明会失去后续操作权限；不能先取消，再依赖缓存或旧的 shareable 结果新建。

先取消指定旧记录并验证，再重新读取合同权限、分享预检查与企业配置，确认用户已确认的对象和期限仍符合当前条件后新增分享并验证；条件变化需用户重新选择时暂停新建。两步不是原子事务：第二步失败时明确报告“旧记录已取消，新分享未完成／结果未知”，不自动恢复旧期限，也不盲目重复新建。保留用户确认的新期限、旧记录 ID、新记录 ID 以及每步结果供继续处理。

## 结果未知与输出

写入超时、解析失败、缺少记录 ID 或回查失败时，先在同一上下文安全查询。不能自动重试、换通道重放或以“存在同接收人同日期记录”证明本次写入成功；重复分享本来允许多条记录。

停止时明确区分：账号或业务权限拒绝、接收人未解析、通道未接入、参数或配置不明确、具体风险分支受阻、提交结果未知。不得把企业开启期限控制或缺少系统整体修复证明单独作为已满足协议的正常创建、批量或取消的拒绝理由。用户只要求预检查时，仅报告检查结果，不附带无关的创建拦截结论。

每次输出包含：动作、合同及实际涉及范围、接收人、对应记录、有效期、已核实结果和仍待确认部分。取消和改期另说明其他权限及下游授权不随本次取消自动失效。不要输出令牌、身份凭据或与本任务无关的合同内容。
