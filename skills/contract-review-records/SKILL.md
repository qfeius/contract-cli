# 我的合同审查清单

用户说“我这个月审查过哪些合同”“列一下本月合同审查记录”等时使用。查询范围是平台归属当前登录人的、当前有效的 CLM 页面审查记录；时间按**审查记录创建时间**计算，不是实际发起时间或完成时间。被后续审查替代的失效记录不在本 Skill 范围内。记录有效不代表审查已完成，按实际审查状态说明。

默认按合同汇总，不逐条展开审查流水。呈现合同名称、当前阶段（如草稿、协商、审批）和可用的最新审查入口；文件名与合同名不同时在同一行补充文件名。上传后尚未保存正式合同的独立预审也保留。当前阶段不是当时审查阶段；支持审查直达且页面权限满足时打开当前结果，不固定指向某次历史任务。

## 保持当前用户和只读范围

- 复用已经确认的 profile、环境、租户和 USER；所有请求显式携带同一 `--profile`、`--as user`。不切换 app 身份，不传调用人覆盖参数或自建授权头。
- 必要时按宿主可发现的 `auth`、`contract-cli-shared` 处理已有授权和续期；合同详情复用 `contract-cli-contract`。缺少依赖或 CLI 能力时说明具体缺项，不猜安装地址或要求用户提供凭证、内部 ID。
- 按实际帮助确认 `contract-cli api call --help` 与 `contract-cli contract get --help` 支持[查询协议](references/query.md)。合同详情保留原始 JSON，并由宿主无损读取长整数 ID；不得先转浮点数再转字符串。本包没有脚本，不依赖 Python。
- 不上传、创建预审、创建审查组、发起/重发审查、生成报告或打开编辑器。不要为补清单读取风险全文；V3 task/info 的历史物化行为不属于这里的查询链。

## 1. 确定期间

沿用用户已给出的期间、时区与条件。缺少期间且也未明确要求全部有效记录时，再询问业务时间范围；不要索取技术 ID。

“本月”按当次用户上下文的当前日期及时区，取月初含界、下月月初不含界；只有日期的闭区间转换为结束日次日零点不含界。时区已有上下文则直接沿用，确实未知且影响归属时再询问。

在结果前说明“平台当前归属本人的有效记录，按记录创建时间筛选，展示合同当前阶段”，并展示采用的期间与时区。不能把创建时间改名为实际发起时间，也不能将平台当前归属解释为不可变的历次实际发起人日志。

## 2. 取全本人有效记录后筛选

先读[查询协议](references/query.md)，执行 history 查询：`appType=CLM`、`reviewMode=all`，省略 businessId，page 从 1 开始，pageSize 为 100。

- 按实际业务成功及分页协议逐页读取，保留全部返回的 taskId、fileId、groupId、业务定位和创建时间；ID 始终保留精确字符串。
- **必须先完成全部分页再按 createTime 筛期间。** 服务端排序依据与 createTime 不同，不能见到某条旧日期就提前停止。
- taskStatus=4 是准备记录，不计为已发起审查；0、1、2、3分别保留为运行、完成、失败、跳过。未知状态保留原值并注明，不能擅自当完成。
- 按 taskId 去重分页重叠。分页总数是全部有效任务数，不是所选期间的合同数。中断、字段异常、并发翻页不稳定时保留已取结果并标部分结果，不把异常当空列表。
- 首个 history 请求就失败、尚未取得成功分页时，报告“查询未成功，未取得审查记录”，不输出空清单或零合同数。本地授权显示有效，也不代表下游服务必然接受该登录态。

## 3. 识别业务对象并读取当前合同信息

仅处理上述已授权结果产生的标识，沿用历史列表的身份上下文。按[查询协议的业务识别分支](references/query.md#业务对象识别)执行。

1. 有可信 CLM businessId：将其作为候选业务 ID，只读查询合同。只有成功且返回的合同 ID 精确一致，才能将其认定为合同；读取真实合同名、当前状态和 pc_url。
2. 仅当合同明确不存在时，再用同一候选 ID 查询预审。认证、权限、网络错误，以及“合同不存在或不可见”的合并错误都不能当作明确未命中。预审成功后核对精确 ID 及业务类型。
3. 旧记录只有 groupId：不能把 groupId 当合同 ID。仅在查询协议允许的 task/status 元数据补充取得可信业务定位时回到上述分支；没有产物则保留为未定位记录，不枚举其他 ID、搜索同名合同或扫描全部合同来猜关联。

合同当前阶段以服务端返回信息及查询协议中已核实的中文状态表展示；已归档等实际状态照实显示，不强行归入草稿、协商、审批。名称缺失时写“合同名未返回”，保留对应文件名，不能把文件名冒充已核实合同名。

独立预审按预审 ID 处理；尚未进入协商显示“未保存／预审”。预审已进入协商却未提供正式合同关联时，标明“已进入协商，正式合同待定位”，不要与同名正式合同合并。

## 4. 按合同汇总并准备链接

- 正式合同按已核实 contract_id 去重；独立预审按类型加 pre_audit_id 去重。不能仅按名称、文件名、groupId 或跨类型数值合并。
- 同一对象保留期间内全部关联 taskId 和文件名，列表只显示一行；可用最新创建时间排序，同时间比较 ID 时不得转浮点数。
- 链接仅按[协议中的链接规则](references/query.md#链接)处理服务端真实返回的页面 URL。放在合同名称之后的“最新审查入口”列；不额外拼接 AI taskId。
- 协商／任务中心及原生分享跳转的当前审查入口、预审工作台与草稿合同入口须分别标明。分享跳转由页面按当前权限选择任务，可能回退合同详情，不能保证审查直达。草稿页未确认支持审查直达时，只能标“合同入口”，不能称“最新审查结果”。没有可信地址时写“未提供”，不得重审来获取链接。

## 5. 呈现和完成判断

默认使用三列：**合同名称｜最新审查入口｜当前阶段**。文件名与合同名不同时在名称格补充；多份文件保留实际名称，可按用户要求展开审查 ID 与记录创建时间。

审查状态与合同阶段分别解释。期间内有运行、失败、跳过或未知状态的记录时，在入口旁标明对应文件或记录的状态；多文件汇总不能隐藏这些状态，也不能给整份合同笼统标成“审查完成”。链接仍按实际用途称“入口”，不能因记录有效就宣称已经有成功结果。

每次均可报告本次实际核实的合同数、预审数及未定位记录数；只有完整分页及汇总结束、没有未定位项或缺失必要信息时，才称其为所选范围的完整总数。预审与正式合同计数分开，不把服务端 task total 当合同数量。清单取数完整与网页审查直达能力分别说明；有原生入口但未实测网页，不等于清单缺记录，也不等于页面验收通过。

存在未定位旧记录、预审转合同关联缺失、缺阶段／结果链接或分页未取全时：

- 先列可核实清单，再保留未定位记录的文件名和可用创建时间，阶段及链接写“未定位”。
- 明确已定位合同、预审及未定位审查记录的数量和原因，不将未定位记录计为额外合同，也不丢弃后宣称查全。
- 缺审查直达时可以返回有依据的合同入口，但说明它的用途；原生入口可能打开比所选期间更新的当前结果。

完成全部分页后的空结果仅表示该范围内没有匹配的当前有效记录，不表示该用户从未审查，也不覆盖已经失效的历史记录。查询不会触发重新审查；结果有效性和阶段以本次读取时点为准。
