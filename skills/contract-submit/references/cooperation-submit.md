# 完成协商与服务端清洁

适用于本 Skill 范围内文件上传类普通单合同在草拟阶段的协商。通过[运行上下文](runtime.md)中的个人权限 Web 通道复用合同页面接口。原协商页供用户自行办理。

## 1. 核适用动作和清洁方式

先按[定位协议](discovery.md)核合同、协商、当前有效轮次、主正文、业务类型和当前身份。区分已在审批、已完成协商、协商中及其他状态。在审批中或已有审批实例时先回查。已完成协商且需要送审时直接进入[完成后的送审回查](#4-分段回查与恢复)。严格详情可能将原码 `3`（协商完成）和 `6`（已结束）都展示为「协商完成」。结合原状态码、合同状态、已有或在途流程和实际提交入口判断首次送审资格。没有完成协商动作的普通草稿、重提或其他流程按其实际送审协议处理。

在草拟阶段、当前轮协商中（`cooperationStageCode=0`、`cooperationStatusCode=2`），核实际模式和按钮对应动作：

| 当前页面业务动作 | 应用的规则 |
| --- | --- |
| 启用正式协商表单（`enableFormCooperation=true`），允许「完成协商并提交审批」 | 对完整正式表单与组合动作确认。完成协商及其后的审批分别验证。 |
| 启用正式协商表单，实际要求「完成协商并前往编辑盖章位置」 | 按该动作核前置和授权。到达签章位置步骤时，按已适配的真实入口交付当前进度，审批状态以流程回查为准。 |
| 普通协商只有独立「完成协商」 | 说明完成后会结束本轮，按[第 3 节](#3-通过接口完成协商)核用户对此动作的明确确认。仅获准完成时，从完成结果回查结束。用户另行确认送审后，按当前正式表单和实际送审入口继续。 |
| 普通协商原页面有独立前置表单 | 在[前置表单协议](cooperation-preform.md)中处理读取、填写、保存及回查。之后按实际动作及授权分流，完成协商前核独立校验；结束后如需送审，重新读取正式申请表单。 |
| 明确只请求保存可编辑的表单 | 走[独立保存](field-save.md)。变更收支类型和交易方另参照[专用映射](#保存收支类型和交易方)。 |
| 无权、确认流程未满足、无法识别实际模式，或出现待发起、已取消、已回滚、审批中等其他状态 | 说明实际状态和受阻步骤。现有送审意图不会触发发起、跳过或恢复协商。 |

**灰度检查。** 对每个确实需要结束协商的对象，在协调自动修订及完成动作之前，取得该合同当前轮实际生效的 `serverCleanFile`。它由本轮发起租户与协商类型决定，后台配置为 `serverGenerateCleanCooperationFile`。优先使用本次已获权、同对象同轮、可复核的协商详情结果。需补读时可沿用已核页面接口 `GET /open-web/web/clm/cooperation/info`，仅传当前 `cooperationId`，匹配 `code=200`、`success=true` 的 `data.serverCleanFile`。该 GET 可能更新确认流程、加入当前轮或标记已读，只在同对象同部署的读取影响已核实且本次授权覆盖时调用。截取所需业务字段，保护编辑器凭证。列表、严格详情、省略的字段、租户曾开通和默认值均不能代替本次实际结果。`shouldCleanFile` 是清洁要求，不能当作服务端模式的证据。已完成协商后从独立申请页首次送审时，使用[该页面自己的普通文件清洁开关和规则](ordinary-file-preparation.md#适用动作与开关)。

- 明确为布尔 `true` 时，核用户权限、确认流程、当前文件以及后续实际动作，再继续本协议。
- 明确为布尔 `false` 时，提示「这份合同需要在智书合同原页面清洁正文并完成协商」，向有权用户提供[原协商页面入口](#原协商页面入口)。协调及完成接口保持未调用。
- 字段缺失、返回值非布尔、无权限、读回失败或同轮配置前后变化时，先补证。仍无法确认时说明「当前轮清洁方式待核实」，停在协商完成之前。不得替用户改灰度或强传 `true`。

继续代办时，核当前 USER 是同租户有效轮次发起人、实际可完成（含 `completable`、只读状态等页面等价证据）。申请审批还需核合同负责人和实际发起资格。用真实当前确认流程与原页面规则核有无前置确认、是否已完成。窄文件或确认检查不足以证明全部资格。完成、只保存、送审各自按实际权限办理。

### 原协商页面入口

优先返回已核原页。需要构造时，仅从[环境映射](runtime.md)取得同环境的合规站点，使用 `/cooperation/detail`、真实 `cooperationId` 与已核来源参数（本人协商列表为 `from=coopList`）。链接只供用户自行办理。用户完成后从[只读回查](#4-分段回查与恢复)接续。

## 2. 确认正式表单及当前正文

1. 表单二合一使用当前轮对应的正式合同表单，按[表单协议](form.md#取得当前表单)核实际可见字段、已填值、AI 建议、必填、权限和备选项。文件上传类纸质单合同可按[已核标准字段映射](field-save.md#二合一纸质单合同的标准字段)保存并回查签约形式、双方主体和其他指定字段，逐步比对原有自定义字段及审批实例。普通协商只完成本轮时，展示目标轮次、将成为最终版的正文及结束本轮影响。已经明确请求送审且实际到了送审入口时，再使用当前正式表单和[送审协议](submit.md)。
2. 对真实动作收取确认。组合动作核完整拟提交表单、实际签约分支和同轮文件，提示用户结束后协作者无法继续修改本轮。按实际顺序核并处理倒签、合规、外部校验及适用付款/收款明细等前置。补填或适用规则改变时，更新完整表单再确认。仅保存按用户确认范围执行。
3. 按真实页面协议保存已确认字段并回查，再用本次业务日期和有效配置执行[倒签校验](submit.md#3-倒签分支)。补充倒签信息后复核更新的表单与动作确认，独立保存倒签原因及说明，回查 `antiDatedSignContract` 中的对应值。复用已保存且一致的值。完成协商前按[已保存正文证据](#已保存正文证据)核本轮主正文与适用附件。
4. 完成协商有可能刷新分类对应的正式审批表单。确认后续办理使用当前有效表单。完成后比对 `formId`、权限、字段及适用规则，变化时把差异纳入完整表单重新确认。电子签位置要求按实际规则处理。

### 已保存正文证据

先用[严格详情](discovery.md#当前状态角色和任务补证)核对象、当前轮和最新有效协商文件，包括 `cooperationFileId`、版本和可得的更新时间或指纹。使用有权、可复核的已保存文件或快照，结合本任务已知编辑状态核实。需要核验正文内容时，同一 USER 通道可用原页面 `GET /open-web/web/clm/cooperation/file/previewOriginal`，query 传实际 `cooperationId` 和最新有效记录的 `cooperationFileId`，用 `--raw` 将响应写入任务私有文件。收到可解析的 DOCX 后核对其内容，并复核同一轮的文件记录和版本仍一致。错误响应按业务失败处理。该快照反映服务端已保存内容，活跃编辑端有待保存内容时，先在原页完成保存再回查。

### 保存收支类型和交易方

- 收支类型走[正式合同更新协议](field-save.md#组装请求)。改为单向收入类且仍是固定总价时，使用 `payType=1`、`contractPropertyTypeCode=0` 和实际的 `totalAmount` 组合。核对完整详情中实际收支类型和原有有效值。
- 收支变化或首次填写对方时，核当前分类、对方控件的可见性和候选。复用原页面 `GET /open-web/web/clm/systemConfig/tradingParty/supplierConfig`，query 为实际 `categoryId`，按[运行上下文](runtime.md)调用。成功取得的有效配置明确启用 `querySupplier=true` 时，按实际适用 `payTypeList` 处理选项和已有对方。已核业务成功且 `data=null` 表示该类型无供方配置，绑定时省略供方查询参数。失败或结果未知时保持待核实。对方被规则要求清除或重选时，展示原值及原因并取得确认。已不存在的对方无需发送清除动作。
- 对方当前为空且用户已经选定实际合法主数据时，用个人通道 `POST /open-web/web/clm/contractTradingParty/createContractTradingParty`，无 query，JSON 传当前合同 `businessId`、实际 `businessTypeCode`、候选的 `tradingPartyId`、`partyName`。主数据 ID 与交易方编码各自保留。实际启用供方查询且本场景适用时才加真实 `categoryId` 和新 `payType`。已存在相同绑定时复用。
- 已完成协商的普通单合同从独立申请页首次送审，纸质签约且用户确认替换唯一现有对方时，按当前表单的选择规则核候选。复用 `POST /open-web/web/clm/contractTradingParty/findBaseTradingPartyInfoByQuery`，无 query，JSON 传 `tradingPartyName`、`pageIndex=1`、`pageSize=10`、`queryScene=CONTRACT_FORM_CANDIDATE`、当前 `categoryId`、`enableTradingPartyConfig=true` 及当前规则适用的 `payType`。认定唯一对应的可用实体前核 `data.content[]`、`hasNext`，需要时按同条件继续分页。选择已启用候选的 `tradingPartyId`、`tradingPartyName` 和编码。
- 上述替换用 `POST /open-web/web/clm/contractTradingParty/updateContractTradingParty`，无 query，JSON 传当前合同 `otherSide` 中原绑定的 `id` 作为 `contractTradingPartyId`，以及用户确认的候选 `tradingPartyId` 和 `tradingPartyName`。实际启用供方查询时带上当前 `categoryId` 和 `payType`。原生替换会重建该对方的签约子记录。发现已有需保留的签约值时，先按实际影响补核并让用户确认。回查同一关系下的新主体及实际签约方式、先盖章方和我方主体。其他阶段或签约方式的替换按各自已核原生协议。
- 业务成功须 `code=200`、`success=true` 并返回绑定记录标识。再读同一合同完整表单，核对 `otherSide` 中对应记录、名称、主数据 ID 和编码。与当前确认表单比较收支、金额、期限、签约和其他关联字段。请求超时、重复提示或结果未知时先回查同一对象。只保存的任务到此结束，未获得完整送审确认时停在已保存状态。

## 3. 通过接口完成协商

在同一环境和 USER 下，只有已确认实际完成动作、已核当前轮 `serverCleanFile=true`、正文保存及实际前置均具备时才进入本段。写前复核当前轮、最新已保存文件和配置与确认一致。调用沿用 `contract-cli api call --channel web --profile '<已核 profile>' --as user --raw`。

| 顺序与原生接口 | 输入、结果与接续 |
| --- | --- |
| 1. `POST /open-web/web/clm/cooperation/autoRevision/coordinate` | Query 为本轮 `cooperationId`、`action=PREPARE_END`、`endType=COMPLETE`，JSON `{}`。请求可能停止自动修订。要求 `code=200`、`success=true` 且 `data=true`，明确成功后才进入完成步骤。调用后若发现轮次或源文件实质变化，暂停并重新核对。 |
| 2. `POST /open-web/web/clm/cooperation/complete` | Query 为同一 `cooperationId` 与已核实际 `serverCleanFile=true`，JSON `{}`。服务端清洁当前已保存文件并完成本轮。二合一首次送审核 `code=200`、`success=true`、`data.businessId` 等于当前合同 ID。回执中的 `cooperationId` 可以为空，按[第 4 节](#4-分段回查与恢复)使用已核协商 ID 验证同轮、状态和最终正文。此请求具有结束协商的真实业务副作用。 |
| 3. 按当前动作处理 | 独立完成的任务到协商与文件回查结束。组合动作刷新实际合同，核实最终版、已确认表单与后续审批入口，首次提交按[送审协议](submit.md)处理。实际要求签章位置时按对应入口接续。 |

灰度关闭、前置失败、权限被拒绝、明确清洁失败或写入结果未知时，在当前阶段停止。返回已核阶段和具体原因。协调及完成均不可作为灰度探测。服务端清洁可能沿用原文件，只有实际文件核验或当前可用的明确结果能证明修订、批注已清除。用户办理的原页面 WPS 流程由页面执行。

## 4. 分段回查与恢复

- **文件。** 用[严格详情](discovery.md#当前状态角色和任务补证)及同通道 `contract-cli contract cooperation history-files list --cooperation-id '<当前协商ID>' --profile '<已核 profile>' --as user` 锁定同轮最终文件。文件记录状态 `4` 表示最终版。再从完成后的正式合同详情取得 `contractText.fileId`，同轮协商文件记录可以保留原文件 ID，正式正文可以绑定新的文件 ID。需要验证最终正文时，使用[合同文件下载](ordinary-file-preparation.md#原页面清洁和回查)复读当前正式绑定。仅回查到绑定时报告最终版及绑定情况。协商源文件和正式文件字节一致且均无修订或批注时，可报告服务端清洁分支成功、正式文件与已保存的内容一致。认定本次删除了修订或批注，须观察清洁前后的实际变化。清洁明确失败或其他必需文件受阻时，停在发起审批之前。
- **协商。** 按同一轮的实际状态确认完成，本路径回读为 `cooperationStatusCode=3`。二合一纸质首次申请随后回查正式合同的 `formId`、已确认的字段和倒签记录，以及当前状态和审批实例。合同的正文、字段、流程或权限实质变化时更新完整表单并确认。若实际走独立申请页替换文件，按[普通送审文件准备](ordinary-file-preparation.md)复核该入口自己的清洁规则。
- **审批。** 已有审批实例时按[审批回查](submit.md#5-结果及未知写入)核记录。二合一纸质单合同首次申请中，协商完成后回查到合同为协商草稿（`contractStatusCode=31`）、审批实例为空时，进入首次送审校验。仍有送审授权、确认有效、正式绑定和适用前置复检通过时，用最新 `formId` 按[首次送审协议](submit.md#4-已核原生动作及接入边界)单独发起。以合同实际流程绑定及同一实例的提交记录、当前节点作为发起证明。仅完成协商的授权止于协商回查。
- **结果未知。** 先用只读接口回查同轮文件、协商状态、表单和审批实例，定位已执行到哪一步。发现同轮已完成且从未发起审批时，在原授权下处理剩余步骤。状态仍在协商或流程为空单独不能证明可重放。等当前动作结果有足够证据后再决定是否需重新确认及接续；避免重复完成协商和重复发起审批。
