# 最终确认、倒签和提交结果

本页接收[表单](form.md)产生的同一份合同的完整拟提交内容。调用使用[运行上下文](runtime.md)中的同一环境、租户及个人授权。保持实际上传正文；财务、主体、签约及审批相关值按原页面规则处理。

用户限定仅保存、文件准备或送审校验时，只执行已授权的相应步骤。即使校验通过，也不调用流程启动、任务提交或附带提交的协商完成动作。回查并报告当前合同状态和审批实例。

## 1. 锁定用户最终确认的内容

表单准备就绪后提示是否提交。用户选择「提交审批」时，沿用[对话内表单](form.md#对话内表单展示)的概览和全表，展示合同名称、编号或明确的目标标识、环境、拟提交值、选填空项和适用提交条件。标明本次修改、系统计算值和既有只读值。若有多份合同，逐份列出并固定用户确认的对象范围。只有用户明确确认这版完整表单，才进入提交校验。第一次表示送审意向、采纳提取值或点击进入确认，不视为最终确认。

确认记录保留环境、租户、员工、合同 ID、业务类型、当前角色与状态、正文 ID/版本、表单与审批绑定、当前任务（如有）、保存前读值和所见全表、变更、候选及附加确认。后续以这些原事实比较，不从展示名反推 ID。用户更改内容、补充倒签或警告确认所依据的事实变化时，更新表单及规则，重新展示完整拟提交表单；旧确认不可复用。权限或状态已不允许时，说明具体原因；已存在流程时先回查，不能用旧确认启动新流程。

## 2. 送审前分流

1. 首次送审写入前，复核合同仍属于本次已定位的上传正文合同，状态和身份允许当前动作，候选和附属字段可按真实协议处理，且目标环境对应的保存、校验、提交及回读协议适用。本人列表命中、可查看或应用身份曾成功都不授予写入权限。任一关键步骤缺少当前 USER 权限、通道或参数依据时，保留已确认内容及受阻步骤。用户明确要求先保存的，在该保存范围独立验证权限和协议，写后回查，停在送审步骤前。
2. 对照实际有效规则执行适用的字段校验、流程模拟、签约校验、自定义/外部校验和相应正文一致性检查。分开报告待补项、警告、硬阻断和未知校验。警告需依据原页面是否允许继续，并将用户选择绑定到这份正文版本、校验结果和确认表单。缺少配置、未返回结果或服务异常均不当作通过。当前为协商完成后从独立申请页首次送审时，按[文件准备](ordinary-file-preparation.md)执行。该分支的清洁在适用的表单保存与自定义/外部校验之后、正文一致性检查和发起之前；后续一致性检查用回查后的实际文件绑定。
3. 原页面对直接「提交」与进入签章位置的「下一步」使用不同链路。只有当前实际动作是直接提交，才准备首次发起。有签章位置、签署人配置或电子签平台校验等前置时，只能按已确认适用的专用协议继续。命中「完成协商并提交审批」时转[表单二合一协议](cooperation-submit.md)。已完成协商、待签章位置、撤回/拒绝后的重提与合同组仍按各自的当前动作和请求协议处理。已在审批中或已处理的合同不重复提交。
4. 本次已明确要求最终确认后检查倒签，按下一节核对并收集适用信息。页面在某些流程先做真实保存，再做外部校验、倒签保存或正常文件准备；执行前复核当前表单和授权，遵循该合同实际顺序，并如实告知阶段结果。有效保存前还需核对字段变更的完整请求参数、独立存储的关联影响和回查方式；遇未适配的准备步骤不能把表单齐全解释为可以绕过。

## 3. 倒签分支

对普通合同申请，当期生效日固定（包括终止日不固定但生效日固定）时，用本次最终确认表单里期限的生效日与**本次提交时的页面业务日期**按日比较。当前倒签配置 `enabled=true`，且生效日早于提交日才命中普通分支。同日不命中；无固定生效日时走其实际页面规则，不能用 AI 建议、终止日期或缺省日期推断普通分支。未成功取得有效配置或无法确定同一页面日期口径，保留「倒签待核实」，不能按未开启继续。

命中时展示实际触发日期、`riskNotice`、当前有效 `reasons` 中的原因选项、原因说明是否必填，以及页面实际要求的证明材料。沿用本合同可核实且仍有效的原有值。原因按页面单选，准确匹配当前配置的 ID 和选项文案；原项失效、同名有歧义或无有效原因时，分别请用户选择、消歧或说明无法继续，不代选。`descriptionRequired=true` 才将说明作为必填，使用 500 字符的当前校验上限；配置 `description` 是输入提示，不代填为用户说明。设置或修改后保留其余原值，重做适用校验，全量展示当前提交表单并重新收取最终确认。

按实际页面协议单独保存该合同的倒签信息并核对，返回用户确认的当前办理分支。选择取消、未确认、接口拒绝、倒签配置在确认后有变或保存未能验证时，不继续执行已确认动作。普通页面的既有值可能因租户倒签显示设置而隐藏，需使用有权且可核的实际结果。

## 4. 已核原生动作及接入边界

普通单合同首次独立送审按实际申请页分流，包括「默认-上传文件」且已跳过协商的草稿，以及原生上传、已完成协商的纸质单合同。已完成协商的对象按当前文件与表单执行适用的[清洁回查和续办](ordinary-file-preparation.md)、[对方替换](cooperation-submit.md#保存收支类型和交易方)、标准字段与倒签保存、预检及审批回查。使用时按[运行上下文](runtime.md)核当前环境、主文、页面分支、权限、表单和已确认的写入范围。通道不可用或所需动作尚未核实时，在对应步骤停止。调用写入或具有副作用的读取需要真实办理依据。

每一项已满足前置的调用直接复用 `contract-cli api call --channel web --profile '<已核 profile>' --as user --raw`，后接实际 METHOD 和下表公共相对路径。按[运行上下文](runtime.md)传已核 query 或 JSON 数据文件；以该 CLM 接口实际 `code=200` 与 `success=true` 再加表中必要业务数据为成功判据。示例中的业务键仅描述形状，实际值全部取本次已核对象。

| 原生动作 | 输入衔接 | 结果、限制与回查 |
| --- | --- | --- |
| `GET /open-web/web/clm/antiDatedSign/config/info` | 无业务 query 或请求体，取当前个人的页面配置。 | 匹配当前租户，记录 `enabled`、`riskNotice`、`reasons`、`descriptionRequired`、`description`。接口虽为 GET，已存在配置的服务分支会经旧原因 ID 转换逻辑保存配置。只在当前操作授权覆盖相应页面行为时读取，不能当作纯读预检；已有符合当前租户、版本与页面口径的有效配置可复用。 |
| `POST /open-web/web/clm/antiDatedSign/contract/save` | 无 query。`businessId` 是本合同 ID；`reasons` 仅一个所选的当前配置项，保留 `id`、`reason`、`order`；`description` 用已确认且实际适用的值。独立业务场景或证明材料只按已核页面要求和映射使用 `actualScenarioCode`、`certificationIds`。 | 独立对象写入，须有当前合同的编辑及提交资格。核成功业务响应所返回的具体选项与说明，并通过有权且已核的同合同读回核对 `antiDatedSignContract`。无依据不清除已有证明材料或历史信息，无真实保存结果不继续。 |
| 正式表单保存 | 按[合同更新协议](field-save.md#组装请求)发送用户已确认的字段变更。 | 按[写后回查](field-save.md#按项回查)确认实际值及关联影响。确认内容发生变化时重新确认送审表单。 |
| `POST /open-web/web/clm/contract/submitCheck` | 无 query。仅对已经保存并回查的当前合同预检。`contractId` 取该合同，首次发起无历史任务参数。取得实际页面规则校验结果时才序列化为 `frontResult`。只做后端预检时，可省略 `frontResult`。 | 记录 `data.invalidAttributes` 及实际业务提示，按返回的字段和原因处理。已核服务异常路径可能返回空错误数组，仍需本对象适用的页面、外部、流程和签约校验有依据。 |
| `POST /open-web/web/clm/form/previewContractFormDefinition` | query 传已保存并回查的 `contractId`，JSON `{}`。 | 审批流程模拟，取 `data` 返回的模拟 ID。模拟读取已保存表单，待用户确认的拟填值先保留于对话中。 |
| `GET /open-web/web/clm/form/previewContractFormDefinition/records` | query `businessId` 为上一步模拟 ID，`formId` 为同合同最新 `formId`，`initiatorId` 为当前已核发起人。 | `data.status=FINISHED` 后核 `data.records` 中实际节点及动态审批人配置。`EXECUTING` 时查询同一模拟结果，超时保留模拟待核实。模拟记录用于校验，实际审批状态按流程回查。 |
| `POST /open-web/web/clm/workflow/runtime/process/start` | 无 query，已验证的普通单合同首次申请使用 `{businessId,businessTypeCode,formId}`。`businessId` 为实际 `contractId`，`businessTypeCode` 是对象实际合同申请类型 `0`，`formId` 取同合同原始详情顶层真实流程表单 ID，核对持久化归属。不能用 `headerFormId` 或其他合同表单。其他参数仅在已核实的对应来源和条件下使用；一致性确认必须来自本次真实正文和实际校验的用户选择。 | 服务按调用人执行合同归属校验及流程前置条件；确认业务响应对象与合同、类型吻合且有真实 `processInstanceId`，再回读合同实际状态和流程绑定。文本、空对象、拒绝与未知结果要区分，不能根据 HTTP 状态或 `success=true` 一项认定发起。 |
| `GET /open-web/web/clm/workflow/runtime/process/records` | 无 body，query 传 `businessId=当前合同ID`、`businessTypeCode=实际类型`、`processInstanceId=已核的流程ID`。流程 ID 来自本合同当前读回和实际启动响应，不使用用户提供的孤立流程 ID。 | 同个人权限下回查流程。用 `data.done[].records[]` 核对实际的 `tenantId`、`businessId`、`businessTypeCode`、`processInstanceId` 及提交记录，`data.todo[]` 的匹配流程节点可说明当前进度。无返回、无权限或关联不符时，不把 `forecast` 或单独的节点名称当实际流程证据。 |

保存动作不提交审批，倒签信息不拼进发起审批的请求体。对纸质签署、文件准备和外部校验，还需真实确认当前页面分支的适用要求；无证明支持时不能默认使用某一租户、某一测试或其他来源合同的成功结果。运行资料与候选对象之间缺失任何参数或结果协议时，报告受阻步骤以及需要验证的事实，不调用审批启动来探测。

期限修改按当前页面规则重算 `fixedValidityDetail`、日期范围和适用时长字段。主体或附件等独立存储动作适用各自协议并分别回查。

## 5. 结果及未知写入

- 保存前登记待执行的动作、目标、确认表单版本及必要摘要。按已确认协议依次执行。后续任一步失败时，区分拟提交值、已保存字段、已保存倒签及实际流程状态，不声称原有写入已回滚。
- 收到提交响应后，使用已授权同对象详情回读实际状态和 `processInstanceId`，再按上表回查审批记录。对有关联协商的合同可用[定位查询](discovery.md)中已核合同基础信息辅助确认；不能用可能返回空结果的协商查询断言无协商合同或流程不存在。确认新流程与本次合同、当前企业和实际返回的流程实例相符，才报告审批发起结果。提交中按实际状态报告。已有流程或读回归因不足时，说明已核当前状态及无法确认本次发起的原因。
- 请求超时、断连、响应矛盾或回读未完成时，标记对应动作的结果待核实。保留尝试记录和可能已保存的内容，先只读查同一对象，不换身份、入口或对象重发。直到有权取得明确流程或确认此前确未发起，才判断下一步；需要再次发起时重新确认对应实际状态和内容。
