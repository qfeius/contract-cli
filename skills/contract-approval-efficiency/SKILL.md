# 合同审批效率统计

统计当前登录用户有权查看的合同审批、盖章和归档任务。支持指定一人、多人、部门、合同或流程实例；所有结果均以当前 USER 权限可见范围为边界，不代表租户全量。

执行前按需读取：

- [运行能力与采集规则](references/runtime.md)：能力预检、人员发现、全量分页、重试、110002 回退、多人合并和完整性状态。
- [统计口径](references/metrics.md)：任务有效性、人员归因、在途、耗时及空部门规则。
- [输出规范](references/output.md)：单人、多人、部门及明细文件的固定结构。

## 业务输入

从用户请求中取得：

- 统计对象：一名或多名人员、一个部门、明确合同或流程实例。姓名和部门名只用于查找候选，后续关联必须使用查询返回的真实 ID。
- 统计周期：采用用户明确周期；未指定时使用最近 30 个完整自然日。时区固定按用户业务时区解释，默认 `Asia/Shanghai`。
- 部门范围：默认包含全部可见子部门；用户明确只看直属成员时才关闭递归。
- 可选节点范围：审批、盖章、归档，默认三类都统计。
- 可选限量：只有用户明确要求试跑或截断时才能设置。正常统计不得限制每位员工的合同数、任务数或总页数。

“今年”从当年 1 月 1 日 00:00 统计到采集时刻；自然月、自然周和日期区间使用半开区间 `[开始, 结束)`，保证结束日期全天被正确纳入。

## 必需能力与停止条件

优先复用当前宿主可发现的通用 Open Web USER 调用器。CLI 入口为 `contract-cli api call --channel web`；MCP 只有在 Tool schema 明确支持任意 Open Web method、path、query、header 和 body，且复用当前 USER 授权时才可使用。

开始业务请求前完成一次能力预检：

1. 调用器存在，实际帮助或 Tool schema 可读取。
2. 支持本 Skill 所需的 GET/POST、分页参数、普通业务 header 和 JSON 响应。
3. 当前 profile、环境、租户和 USER 授权一致；不得切换为 APP 或其他用户。
4. 可用的表格能力能够生成 `.xlsx`；若没有，只要求能够写 UTF-8 BOM CSV。

通用 Open Web 能力不存在或不兼容时，停止并返回 `CAPABILITY_MISSING`，说明缺少“通用 Open Web USER 调用能力”。不得把业务专用的“当前用户任务”Tool扩展解释为可查询任意人员，也不得猜安装地址或假设某个固定 CLI 版本具备能力。

只允许使用用户可用的 USER 通道。禁止通过 MySQL、PostgreSQL、只读业务库、内部数据库 MCP、日志平台、APP 身份或后台直连补数。

## 执行主线

### 1. 固定范围和人员清单

先确定 `analysis_subject`：

- 用户明确点名一人或多人：`people`。
- 用户按部门查询：`department`，即使部门当前只有一人也不改成 `people`。
- 用户按合同、流程实例或其他业务范围查询：`other`。

按姓名查人员候选，按部门名查部门候选。唯一候选可直接采用；重名或同名部门必须向用户展示名称、当前部门等可区分信息，由用户选择。不要要求用户提供内部 ID。

部门默认递归所有可见子部门，逐部门读完直属成员分页，按真实 `employeeId` 去重。保存完整人员清单，零任务人员也必须保留。

### 2. 全量发现已办和待办

对每位目标人员，使用目录返回的真实 `larkId` 分别读取：

- 已办任务 `task_status=1`；
- 待办任务 `task_status=0`。

人员和任务状态各自维护游标，逐页读取至协议终点。第一页较短不能作为结束依据；重复页、游标不前进或游标缺失应停止该分页流并记录缺口。默认不设置合同数、任务数或页数上限。

多人查询直接在同一执行中合并，不能要求调用者手工合并中间文件：

- 人员按 `employeeId` 取并集；
- 任务按 `(process_instance_id, task_instance_id)` 去重；
- 同一任务的 `discovered_for_employee_ids` 取并集；
- 流程实例按 `processInstanceId` 合并，来源任务和匹配人员取并集；
- 状态、时间、业务归属或节点字段冲突的任务保留诊断，但排除统计。

### 3. 读取流程记录和合同元数据

按发现得到的真实 `processInstanceId` 读取流程记录。只有明确合同范围而没有实例 ID 时，才先读合同详情取得实例 ID。保留 `done` 和 `todo`，`forecast` 不参与统计。

合同名称和编号按真实业务键补全。普通合同 `contract/info` 返回业务码 `110002` 时，只调用一次 `contract/briefInfo`：

- 回退成功且合同 ID 一致时，采用返回的合同名称、编号、业务类型和流程实例 ID；
- `110004`、未授权、对象不存在或参数错误不得回退；
- 回退仍失败时保留元数据缺口，不伪造名称或编号。

元数据失败不能自动把已经完整取得的任务记录判为缺失；按运行参考分别维护流程记录、业务元数据和人员归因证据状态。

### 4. 归因、对账与统计

使用任务中心的 `(process_instance_id, task_instance_id, discovered_for_employee_ids)` 与流程记录精确连接。多人会签、或签或串行节点中，只要任务中心能够确认实际处理人及其任务时间，就计入该人的效率；多人节点本身不是排除理由。

自动结束、取消、自动跳过、无法唯一归因、任务 ID 缺失、人员清单冲突或关键字段冲突的记录保留在明细中，但不进入个人效率。没有原始个人任务时，只有完整且与历史实例、定义和节点严格匹配的单人证据才能回退归因。

按[统计口径](references/metrics.md)计算所有指标。统计过程保留原始秒数；报告表格和明细文件统一展示为中文时分秒，例如 `1小时52分30秒`、`31分15秒`、`20秒`。

### 5. 生成报告和明细

严格按[输出规范](references/output.md)路由：

- 单人：只显示一张个人效率表，审批、盖章、归档以“节点类型”区分。
- 多人：只显示个人效率统计，审批、盖章、归档分别一张表。
- 部门或其他范围：显示审批效率总览、效率洞察、三张个人表和明细文件。

所有模式都先写统计周期、统计数据范围和统计周期内涉及合同数。不得显示“第一部分”“第二部分”“第三部分”等编号文案。面向用户的报告不展示原始任务量、候选合同量、流程记录读取量或重试次数；这些只留在结构化诊断中。

明细优先生成 Excel；表格能力不可用或导出失败时生成 UTF-8 BOM CSV，并简要说明回退原因。长 ID 以文本保存，不能转为浮点数。

## 重试、授权和部分结果

只读调用使用[运行参考](references/runtime.md)中的统一三次有界重试。一次重试成功不应让整份报告变成 `partial`；三次耗尽后保留已取得数据、失败分页流和续读位置。

授权过期时沿用调用器自己的 USER 重新授权流程，授权完成后从失败步骤继续原请求。不得索取、记录或转述用户凭证。

最终状态：

- `complete`：目标清单、所有人员的已办/待办分页、涉及流程记录和必要归因证据均完整；可选元数据缺失单独披露。
- `partial`：仍可生成部分统计，但存在未完成分页、无权读取的流程、关键对账冲突或归因证据缺口。缺失部分不能按零解释。
- `not_found`：姓名、部门、合同或流程对象未找到；不等同于效率为零。
- `capability_missing`：宿主缺少必要通用调用或文件导出能力，未执行统计。

只有 `complete` 才能表述为“统计完成”。`partial` 报告必须在表格前用一句话说明哪些业务范围未覆盖，不能评价人员表现。

## 完成标准

一次请求完成时必须同时满足：

- 时间、对象、人员清单和部门递归范围明确；
- 每名人员的已办和待办均已完整分页，或明确标记缺口；
- 流程记录与任务中心完成精确对账；
- 多人任务按实际处理人归因，无法归因者已排除并保留明细；
- 表格结构符合对象路由；
- Excel 或 CSV 明细文件已实际生成并可打开；
- 报告准确披露可见范围、状态和缺口，不把缺失数据写成真实零。
