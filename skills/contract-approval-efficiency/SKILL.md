# 合同审批效率统计

开始前必须读取 [接口契约](references/api-contract.yaml) 和 [固定用户授权规范](references/user-authorization.md)，再读取 [执行与采集](references/execution.md) 和 [统计口径](references/metrics.md)；按姓名/部门查询时再读取 [人员与合同发现](references/discovery.md)。所有通道和业务配方仅使用 USER 身份；授权完成后继续原始统计请求。

本 Skill 面向客户账号运行，数据源只允许客户可用的通用 Open Web USER 通道：已验证的 `contract-cli`，或符合 `universal_open_web_call` 契约并完成本次配方验证的 MCP。不得调用 MySQL、PostgreSQL、只读业务库、内部数据库 MCP、日志平台或后台直连接口补数；即使当前运行环境提供这些工具也不能使用。通用通道未取得的数据保留为覆盖缺口，不能改用内部权限绕过，也不能按零处理。

## 输入与范围

- 环境为本版已验证的 `contract-test` / test / user。其他环境须单独验证，不切换生产 profile。
- 优先用户时间范围；默认最近30个完整自然日，时区 Asia/Shanghai。“今年”取年初至采集时刻。已处理按任务结束时间 `[开始,结束)` 筛选；在途是采集时快照。
- 用户指定合同/流程实例优先。只有姓名或部门名称时解析真实人员，重名选定候选；部门默认包含子部门。人员和部门ID仅作内部关联，不作为个人统计表展示列。
- **默认分页取完当前权限可见范围，不限制每位员工合同数量、合同页数、部门数量或成员页数。** 不再设置200份、20页或自动试跑3份等隐含边界；仅用户明确要求试跑/截断时传正数限额。异常、重复页和游标问题仍中止并披露缺口。
- 部门人员采用当前组织快照，不保证还原离职员工和历史调岗。参与候选不代表实际已处理。
- 先按用户提问确定分析对象：明确点名一人或多人属于 `people`；按部门查询属于 `department`；按合同、流程或未指定人员范围属于 `other`。即使部门当前只有一人，仍按 `department` 输出。

## 执行前检查

- 本包采用 `HYBRID`：先检查 CLI，再检查 MCP。CLI 必须存在、版本满足契约，并由 `contract-cli api call --help` 确认支持通用 Open Web 调用；只有 CLI 不存在、版本不满足或通用命令不兼容时，才检查 MCP。
- MCP 只有在存在符合统一契约的 `call-open-web-api` Tool、Schema 可读且 USER 授权可恢复时才算可用；业务专用 Tool 不能冒充通用调用能力。当前交付的真实运行证据覆盖 test CLI，MCP 状态为 `UNVERIFIED`，使用前必须逐配方补充 HTTP 与业务成功证据。
- 两种通道都不可用时，按接口契约的 `GUIDE_INSTALL_CLI` 处理：只使用用户批准的本地交付包或可信来源，先说明安装和 profile 变更，再取得所需授权；不得猜下载地址或静默安装。恢复后继续原始统计请求。
- CLI 和 MCP 均只使用 USER。授权状态、Device Grant 展示、单次 complete、重试及续办规则以 [固定用户授权规范](references/user-authorization.md) 为准，不接收原始凭证。

## 执行

1. 按 `runtime.execution_mode` 选择已验证通道。CLI 路径检查 `api call --channel web` 与同一 test 用户授权；MCP 路径把接口契约中的 method、`open_web_path`、query、普通业务 header 和 body 映射到标准 `call-open-web-api` Tool。不得传服务地址、Relay 地址或认证材料，也不切换他人身份。
2. 有姓名/部门条件时运行 `scripts/discover_businesses.py`，默认按真实目录 `larkId` 分页读取 BPM 原始已办、待办任务；已有明确业务范围则加 `--resolve-only`。保存完整 `employees`，零任务员工也保留。正常查询省略所有 max 参数（默认0，不限量）。**不得以 `APPROVE_AUTHORITY` 参与索引作为统计的必需筛选条件**：实际审批任务可能存在，但此异步字段漏项。旧索引结果不能直接续读成新版完整结果。
3. 运行 `scripts/collect_records.py --with-definition-metadata`，按发现结果中的真实流程实例读取全部记录，再关联真实业务类型、合同名称和编号，并保留与当前实例绑定的定义元数据。脚本内部调用 CLI 时显式传 `--profile contract-test --as user` 和 `Timezone-Offset: -480`。BPM任务入口成功为 `success=true,code=0`，CLM记录入口为 `success=true,code=200`，分别验证；保留权限拒绝、失败分页及原始任务与记录不一致的缺口。
4. 采集 bundle，保留发现阶段的完整 `task_records`，以及流程 `done/todo` 节点和记录。任务中心的 `(process_instance_id, task_instance_id, discovered_for_employee_ids)` 是个人归因证据；流程记录提供节点类型、动作、起止时间和业务归属。**不得在采集时先过滤其他人员、窗口外任务或自动记录**。
5. 对采集 bundle 运行 `scripts/collect_participant_evidence.py`，再运行 `scripts/reconcile_records.py` 对账原始任务与流程记录。多人节点不再整体排除：任务中心能明确对应到一个实际处理人的已办任务，或明确对应到目标人员的待办任务，计入该人员效率；或签中自动结束、取消、无人工有效动作的记录仍不计。任务中心仍归因多人、与人员清单不一致或缺少必要证据时才排除并提示。没有原始任务清单的显式合同/流程查询，回退历史完整单人证据。
6. 运行分析器，一次生成结构化报告及明细：

   ```bash
   python3 <skill-directory>/scripts/analyze_records.py \
     --input <补证bundle.json> --markdown <report.md> --json <report.json> \
     --details <审批效率明细.xlsx> --analysis-subject <people|department|other>
   ```

   分析器优先尝试 Excel，依赖或生成失败自动输出同名 UTF-8 BOM CSV，并在报告中写明原因。Codex 中按表格工具要求加载已有运行依赖；也可用 `--node`、`--node-modules` 指定，不能静默下载或打包个人运行环境。JSON 保留原始秒数与内部关联ID。
7. 核对总览与明细的 `included_overview`，个人统计与 `included_personal`。根据分析对象选择下述输出结构，并给出实际已生成的明细文件链接，不只给命令或口头承诺。

## 输出结构

先说明 **统计周期**（起止时刻与时区）和 **统计数据范围**（对象、当前部门及子部门口径、环境、来源），并且只展示 **统计周期内涉及合同数**。该数量按有效完成任务对应的 `(businessTypeCode,businessId)` 跨审批、盖章、归档去重；具体人员模式只统计能归因到所选人员的任务。不要在面向用户的 Markdown 或 Excel 中展示原始任务量、候选合同量、流程记录读取量等采集过程数字；存在接口、权限或对账缺口时只做简短提示，详细数量保留在 JSON 诊断中。

### 具体人员模式

用户明确询问一人或多人的效率时，bundle.meta.analysis_subject 写 `people`，分析器传 `--analysis-subject people`。只展示 `个人效率统计`，**不得输出审批效率总览、效率洞察，也不得出现“第一部分”“第二部分”“第三部分”标题**。

只查询一名人员时，审批、盖章、归档合并为一张表，以“节点类型”区分，固定字段为：

| 姓名 | 节点类型 | 处理合同数 | 审批通过次数 | 审批拒绝次数 | 在途待办任务数 | 总用时(h) | 平均用时(h) | 最长用时(h) | 最短用时(h) |
|---|---|---|---|---|---|---|---|---|---|

查询两名及以上人员时，审批、盖章、归档分别一张表。每张表列出所选人员清单中的所有人，包括没有有效处理数据的人员；字段顺序固定为：

| 姓名 | 处理合同数 | 审批通过次数 | 审批拒绝次数 | 在途待办任务数 | 总用时(h) | 平均用时(h) | 最长用时(h) | 最短用时(h) |
|---|---|---|---|---|---|---|---|---|

无有效样本时数字显示0，用时显示0.00。单人合并表下集中提示三类节点的任务中心归因数量与剩余排除数量；多人分表时逐表提示。明细文件继续生成并以普通文件链接附在个人表后，不把它渲染成编号章节。

### 部门或其他范围模式

按部门、合同、流程或其他范围分析时，bundle.meta.analysis_subject 分别写 `department` 或 `other`，保留以下完整结构。

#### 第一部分：审批效率总览

按审批、盖章、归档各一行，用一张总览表展示：

| 节点类型 | 处理合同数 | 审批通过次数 | 审批拒绝次数 | 在途合同数 | 总用时(h) | 平均用时(h) |
|---|---|---|---|---|---|---|

表格下必须有**效率洞察**：解释不同阶段的处理量、用时与在途情况，提示有效样本及覆盖限制。仅基于可见数据提出核对方向，不凭自然等待时间评价员工表现。

#### 第二部分：个人审批效率统计

**审批、盖章、归档分别一张表，不能混在同一张个人表。** 每张表列出统计人员清单中的所有人，包括没有有效处理数据的人员；字段顺序固定为：

| 姓名 | 处理合同数 | 审批通过次数 | 审批拒绝次数 | 在途待办任务数 | 总用时(h) | 平均用时(h) | 最长用时(h) | 最短用时(h) |
|---|---|---|---|---|---|---|---|---|

无有效样本时数字显示0，用时显示0.00。个人表不显示人员ID，节点类型由各表标题表达。每个节点下说明多人节点排除的节点数、任务数、合同数，以及单人条件待确认的数量。多人包括会签、或签等；这些记录仍保留在符合范围的总览与明细中，因此个人合计不一定等于总览。缺权限/数据未取全不能解释成真实无审批。

#### 第三部分：审批明细

交付可下载的 **Excel `.xlsx`**；生成失败时交付 **CSV `.csv`** 并说明原因。每条范围内任务记录一行，不因多人候选而复制成多行。前九列固定：

合同名称、合同ID、合同编号、节点名称、操作人、操作结果、进入时间、完成操作时间、用时(h)。

之后保留节点类型、流程实例ID、任务ID、计入总览、计入个人统计、排除原因，方便对账。多人、自动操作、无效时间等排除记录和在途待办也保留并标识；时间缺失留空，不伪造零用时。ID按文本保存，保留长整数精度。

## 核心口径

- 处理合同数按 `(businessTypeCode,businessId)` 去重；通过/拒绝按有效任务次数。重审多次可对应一份合同，不能混用合同数与任务数。
- 平均用时=有效任务总用时÷有效处理次数；包括等待和非工作时间，不是实际劳动时长，也不是并行节点整体周期。
- 总览在途按合同去重；个人在途按待办任务计数。审批、盖章、归档分别统计，跨阶段合同不能简单相加当成总合同数。
- 个人归因优先使用原始任务中心数据。多人会签/或签节点中，每个实际完成的人工任务按自己的进入和完成时间计入对应人员；或签失败候选的自动结束记录不计。任务中心无法唯一归因时才排除。`taskModeCode` 只说明模式，不能代替个人任务证据。
- 历史任务优先采用自己的业务ID和类型；无法证明合同归属时在明细留空并列缺口，不把当前合同名称/ID套给历史任务。
- JSON 另保留按部门和流程节点的聚合数据供明确追问使用，不替换上述默认输出结构。

## 权限与确认

- 所有配方都是只读 USER 请求，不需要业务写入确认；安装 CLI、创建或修改 profile 等本机变更仍按固定授权规范先说明再执行。
- 目标姓名或部门只作为业务筛选，不代表切换成被查询人的身份。无权限记录保持缺口，不能尝试 APP、数据库或其他用户授权。

## 失败处理

- 同时检查传输状态、HTTP 状态和配方声明的业务 `success/code`；HTTP 200 不能单独解释为成功。
- 授权失效按固定用户授权规范恢复，完成后只续办原请求；权限拒绝、业务失败或重试耗尽时标记 `partial`，不改写为空集合或真实零。
- 只读请求仅按采集脚本的有界策略重试。发生超时或结果未知时不得无限重试，也不得通过数据库、内部接口或切换身份补数。

## 交付状态

`RUNNABLE`（test / CLI / USER）。CLI 已覆盖必需配方的真实成功样本；MCP 和生产环境未验证。独立离线验收只验证冻结包能否自行指导请求映射、授权、结果解释与失败处理，不提升真实运行成熟度。
