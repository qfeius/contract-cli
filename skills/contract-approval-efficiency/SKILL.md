# 合同审批效率统计

统计合同审批、盖章和归档效率，支持人员、部门、系统角色的当前成员、合同或流程实例。目录用于确定人员；查询任务时由 `getVisibleTasks` 校验目标人员是否在当前 USER 的角色负责部门范围。指标和明细仅纳入当前 USER 成功读取流程记录的合同。

执行前按需读取：

- [人员、部门和角色发现](references/discovery.md)：中文姓名、部门路径、组织树和角色成员。按人员、部门或角色统计时读取。
- [运行能力与采集规则](references/runtime.md)：能力预检、范围边界、任务全量分页、合同/流程链路、重试、元数据回退、多人合并和完整性状态。
- [统计口径](references/metrics.md)：任务有效性、人员归因、在途、耗时及空部门规则。
- [输出规范](references/output.md)：单人、多人、部门及明细文件的固定结构。

## 业务输入

从用户请求中取得：

- 统计对象：一名或多名人员、一个部门（名称或路径）、一个系统角色、明确合同或流程实例。按角色统计默认取当前启用的系统角色成员。后续关联使用已核实的真实 ID。
- 统计周期：采用用户明确周期；未指定时使用最近 30 个完整自然日。时区固定按用户业务时区解释，默认 `Asia/Shanghai`。
- 部门范围：默认包含全部可见子部门；用户明确只看直属成员时才关闭递归。
- 可选节点范围：审批、盖章、归档，默认三类都统计。
- 可选限量：只有用户明确要求试跑或截断时才能设置。正常统计不得限制每位员工的合同数、任务数或总页数。

“今年”从当年 1 月 1 日 00:00 统计到采集时刻；自然月、自然周和日期区间使用半开区间 `[开始, 结束)`。若用户请求的自然周期尚未结束，实际结束时刻取采集时刻，不能把未来的月末、周末或次日写入统计周期，也不能说明未来新增任务会自动进入本次结果。

## 必需能力与停止条件

页面合同、流程和目录接口复用当前宿主可发现的通用 Open Web USER 调用器。CLI 入口为 `contract-cli api call --channel web`；MCP 只有在 Tool schema 支持本次所需的 Open Web 方法、路径、参数和响应，且复用当前 USER 授权时才可使用。人员、部门、角色模式通过同一 USER 调用带部门权限校验的 `getVisibleTasks`。目录和角色接口按其自身的业务权限使用。

开始业务请求前完成一次能力预检：

1. 调用器存在，实际帮助或 Tool schema 可读取。
2. 支持本 Skill 所需的 GET、分页参数、普通业务 header 和 JSON 响应。
3. JSON 读取链能把超过安全整数范围的合同、人员、任务和游标 ID 保持为原始文本或任意精度整数；不能无损解析时不得执行相关分页流。
4. 当前 profile、环境、租户和 USER 授权一致；不得切换为 APP、管理员或其他用户扩大读取范围。
5. 可用的表格能力能够生成 `.xlsx`；若没有，只要求能够写 UTF-8 BOM CSV。

通用 Open Web 能力不存在或不兼容时，停止并返回 `CAPABILITY_MISSING`，说明缺少“通用 Open Web USER 调用能力”。不得把业务专用的“当前用户任务”Tool扩展解释为可查询任意人员，也不得猜安装地址或假设某个固定 CLI 版本具备能力。

`people`、`department`、`role` 模式按[运行参考](references/runtime.md#人员部门和角色模式的能力与权限判定)区分入口不可用、登录授权失效和目标员工超出负责范围。禁止回退旧 `getTasks` 或改用仅查本人的任务列表。部门或角色名单完整且确实无人时不需要查询人员任务。

只允许使用用户可用的 USER 通道。禁止通过 MySQL、PostgreSQL、只读业务库、内部数据库 MCP、日志平台、APP 身份或后台直连补数。

## 执行主线

### 1. 固定分析范围

先确定 `analysis_subject`：

- 用户明确点名一人或多人：`people`。
- 用户按部门查询：`department`，即使部门当前只有一人也不改成 `people`。
- 用户按系统角色查询：`role`，即使当前只有一位成员也仍输出角色报表。
- 用户按合同、流程实例或其他业务范围查询：`other`。

`people`、`department`、`role` 按[发现流程](references/discovery.md)确定范围。关键词结果为空时，使用已获准的组织目录或请用户补充业务线索。部门路径逐层核对，到目标部门后再读成员。角色模式读取角色自身的绑定成员。人员名单按真实 `employeeId` 去重，保留完整查得的零任务成员。

### 2. 人员、部门和角色范围：全量发现已办和待办

对每位目标人员使用目录返回的真实 `larkId`，按[新任务接口配方](references/runtime.md#人员任务-getvisibletasks)分别读取：

- 已办任务 `task_status=1`；
- 待办任务 `task_status=0`。

人员和任务状态各自维护游标，按配方读取至终点。默认不设置合同数、任务数或页数上限；用户明确要求试跑时由客户端按取得的唯一任务或实例数截断并标记样本限制。任务查询被拒绝的人员保留为覆盖缺口，不按零值处理，也不从其他人的可读流程反推其效率。

多人查询直接在同一执行中合并，不能要求调用者手工合并中间文件：

- 人员按 `employeeId` 取并集；
- 任务按 `(process_instance_id, task_instance_id)` 去重；
- `discovered_for_employee_ids` 只记录“该任务由哪个本次目标人员的独立查询流命中”，对这些目标人员取并集；不得把响应中的全量 `assignee_ids` 写入此字段；
- 流程实例按 `processInstanceId` 合并，来源任务和匹配人员取并集；
- 状态、时间、业务归属或节点字段冲突的任务保留诊断，但排除统计。

发现结果只是候选。每个候选实例都必须在当前 USER 下成功读取 `process/records` 才能进入任何完成、在途、个人或部门指标。110004、无权读取或记录失败的实例标记 `partial`，不按零处理，也不把其任务元数据写入面向用户的明细。

### 3. 合同或流程范围：直接读取流程事实

`analysis_subject=other` 不执行按人员反查任务：

1. 用户给出普通合同 ID 时，调用 `contract/info` 取得真实 `processInstanceId`；合同组类型 `10/17` 在没有已验证合同组详情能力时返回范围未覆盖，不能套用普通合同接口。
2. 用户给出流程实例 ID 时直接使用该实例；不得从名称或合同编号推算实例 ID。
3. 在当前 USER 下调用 `process/records`，读取该实例的 `done` 和 `todo`。调用失败或 110004 时停止该对象统计并返回 `partial` 或 `not_found`，不得使用无权限校验的任务元数据或历史实例接口替代。
4. 从流程记录的 `assigneeEmployees` 按真实 `employeeId` 去重形成“处理人清单”：done 中唯一人员是实际处理人，todo 中人员是当前候选/经办人。合同/流程个人表只列这份清单，不依赖人员任务接口，也不需要 `discovered_for_employee_ids`。
5. 使用流程记录中的 `processTaskInstanceId`、`taskStatusCode`、`commandTypeCode`、`createTime` 和 `endTime` 作为任务事实源。done 记录仍含多名人员时保留在范围总览和明细，个人归因标记为歧义；todo 分别计入记录列出的目标候选人的在途。

### 4. 读取流程记录和合同元数据

按发现得到的真实 `processInstanceId` 读取流程记录。只有明确合同范围而没有实例 ID 时，才先读合同详情取得实例 ID。保留 `done` 和 `todo`，`forecast` 不参与统计。

合同名称和编号按真实业务键补全。`110002` 是通用系统错误，不能解释为合同类型或对象不存在。普通合同 `contract/info` 返回 110002 时先按只读重试规则处理；重试耗尽后，只有对象已由可信来源明确为普通合同时，才能调用一次 `contract/briefInfo` 尝试补全可选元数据：

- 回退成功且合同 ID 一致时，仅采用真实返回的合同名称、编号、业务类型和流程实例 ID；这不能替代 `process/records` 权限闸门；
- `110004`、未授权、对象不存在或参数错误不得回退；
- `briefInfo` 返回空、ID 不一致或失败时保留元数据缺口，不伪造名称或编号。

元数据失败不能自动把已经完整取得的任务记录判为缺失；按运行参考分别维护流程记录、业务元数据和人员归因证据状态。

### 5. 归因、对账与统计

人员、部门、角色模式使用任务中心的 `(process_instance_id, task_instance_id, discovered_for_employee_ids)` 与流程记录精确连接；人员归因只使用该目标员工通过新任务接口取得的候选与流程记录的交集。done 记录中 `assigneeEmployees` 的唯一人员是实际处理人；todo 记录中的人员是待办候选/经办人。`getVisibleTasks.assignee_ids` 只作候选发现和诊断。

在人员、部门、角色模式下，会签、或签或串行节点的 done 唯一实际处理人、todo 的每个目标候选人均须同时属于该任务的 `discovered_for_employee_ids`，才计入该人。完成用时按该任务自己的进入和完成时间计算。候选人数多不影响唯一实际处理人的归因；done 仍有多个实际人员时标记归因歧义并排除个人统计。

自动结束、取消、自动跳过、无法唯一归因、任务 ID 缺失、人员清单冲突或关键字段冲突的可读记录保留在明细中，但不进入个人效率。历史表单定义仅在当前调用人本身具备管理员权限时作为可选审计证据；普通 USER 不尝试提权，缺少其他归因证据时将 `attribution_evidence_status` 标为 `partial`。

按[统计口径](references/metrics.md)计算所有指标。统计过程保留原始秒数；报告表格和明细文件统一展示为中文时分秒，例如 `1小时52分30秒`、`31分15秒`、`20秒`。

### 6. 生成报告和明细

严格按[输出规范](references/output.md)路由：

- 单人：只显示一张个人效率表，审批、盖章、归档以“节点类型”区分。除统计周期、数据范围、涉及合同数、表格、必要的一句覆盖说明和明细链接外，不得增加“要点说明”、洞察、同比、异常清单或技术原因列表。
- 多人：只显示个人效率统计，审批、盖章、归档分别一张表。
- 部门：显示部门审批效率总览、效率洞察、三张个人表和明细文件。
- 角色：显示角色审批效率总览、效率洞察、三张成员个人表和明细文件，数据范围写明使用当前成员快照。
- 合同或流程：显示该范围的流程节点效率、处理人效率表和明细文件；不使用部门总览或部门人员补零口径。

所有模式都先写统计周期、统计数据范围和统计周期内涉及合同数。不得显示“第一部分”“第二部分”“第三部分”等编号文案。输出 Markdown 表格时必须使用未转义的 GitHub Flavored Markdown 表格，表格前后各留一个空行，不放入代码块、不缩进，也不把整张表作为普通文本输出。面向用户的报告不展示原始任务量、候选合同量、流程记录读取量、重试次数、内部枚举或接口降级细节；这些只留在结构化诊断中。

生成报表时，明细优先用 Excel；表格能力不可用或导出失败时生成 UTF-8 BOM CSV，并简要说明回退原因。长 ID 以文本保存，不能转为浮点数。

## 重试、授权和部分结果

只读调用使用[运行参考](references/runtime.md)中的统一三次有界重试。一次重试成功不应让整份报告变成 `partial`；三次耗尽后保留已取得数据、失败分页流和续读位置。

授权过期时沿用调用器自己的 USER 重新授权流程，授权完成后从失败步骤继续原请求。不得索取、记录或转述用户凭证。

最终状态：

- `complete`：适用模式的目标清单和任务分页完整，所有纳入指标的流程均在当前 USER 下成功读取，必要归因证据完整；可选元数据缺失单独披露。
- `partial`：仍可生成部分统计，但有目标员工任务未获授权、分页未完成、流程无权读取或存在归因证据缺口。受影响指标显示 `—`。
- `needs_input`：姓名索引空、候选不唯一或权限内目录无法确认时，等待用户补充所在部门、路径、别名等业务线索。
- `not_found`：在已完整核实的可查范围内没有对应部门、启用角色、合同或流程对象。
- `permission_denied`：角色名单不可读、任务接口拒绝全部目标员工或拒绝当前用户访问该路由。明确是员工范围拒绝时，说明应核对角色成员配置的负责部门。
- `capability_missing`：宿主缺少必要通用调用、新任务路由、可验证的完整分页或文件导出能力，未执行统计。

只有 `complete` 才能表述为“统计完成”。`partial` 报告按[输出规范](references/output.md)在结果表格之后用一句话说明哪些业务范围未覆盖，不能评价人员表现。

## 完成标准

一次请求完成时必须同时满足：

- 时间、对象及适用的人员清单、部门递归、角色成员或合同/流程范围明确；
- 人员/部门/角色模式下每名人员的已办和待办均经新接口的部门权限校验且完整分页，或明确标记缺口；合同/流程模式不依赖人员任务发现；
- 每个纳入指标的实例都已由当前 USER 成功读取流程记录；无权读取的候选已排除并标记覆盖缺口；
- 人员/部门/角色模式的流程记录与任务中心完成精确对账；合同/流程模式直接以流程记录建立处理人清单；
- 多人任务按实际处理人归因，无法归因者已排除并保留明细；
- 表格结构符合对象路由；
- 已生成报表的请求附有可打开的 Excel 或 CSV 明细文件；
- 报告准确披露可见范围、状态和缺口，不把缺失数据写成真实零。
