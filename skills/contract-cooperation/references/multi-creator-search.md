# 多发起人查询与合并

用户指定多个发起人时，使用现有单值 `create_user_id` 逐人查询，最终取结果并集。这是 Skill 编排；没有新增 CLI 命令、人员数组参数或服务端合并分页。

## 人员与共同条件

1. 按 [人员技能](../../contract-cli-employee/SKILL.md) 解析姓名；结合用户已给出的姓名、部门等信息确认候选，重名未消歧时询问用户，不直接选择第一条。使用真实开放 `user_id`，不用内部 employeeId。
2. 按解析后的 user_id 去重，保留用户指定顺序；同一人重复出现或有多个称呼时只查询一次。未找到人员或尚未消歧，不能作为该人没有协商的证据，也不能宣称所有发起人已查完。
3. 固定同一 profile、user 身份、环境与共同条件。每个人复制相同的范围、顶部视图、关键词、状态、类型、日期、部门、角色和 order；只替换 `create_user_id`。不能为了命中结果扩大范围或删条件。

例如：用户已明确“我的协商中，甲或乙发起且已完成的协商”，分别准备两个文件，使用同一命令：

```bash
contract-cli contract cooperation search --input-file creator-a.json --profile <profile> --as user --output json
contract-cli contract cooperation search --input-file creator-b.json --profile <profile> --as user --output json
```

两份 JSON 的共同部分为 `search_tab_enum_code=1`、`cooperation_query_status_codes=[4]`、`page_size=20`；`create_user_id` 分别填写已确认的甲、乙 user_id。仍需带上用户的其他条件。不把多个 ID 拼成逗号字符串，也不传 `create_user_ids`、页面内部 ID 字段或姓名。

## 每个人独立分页

- 每个人的首轮请求均清除 `page_token`；切换人员时不继承上个人的 token。为每个人单独记录已用 token 和查询完成状态。
- 检查进程退出码和响应业务 code/success。成功后读取 `data.items`、`data.has_more`、`data.page_token`。
- 用户要求完整的多人结果时，先读完当前人的所有页，再查下一个人。`has_more=false` 即该人结束，即使返回非空 token 也不继续；`has_more=true` 则用该人的新 token 继续，其他条件保持不变。
- `has_more=true` 但 token 缺失、重复，或分页标志缺失/类型异常时，停止该人的分页并标记未完成；可继续其他已确认人员，但最终只能报告部分结果。不得把异常当末页或循环重试。
- 用户明确限制查询页数、请求量或结果数量时遵守限制，并说明仅获取部分结果；不声称完成全部人员的全量查询。

## 合并、去重与展示

- 去重键只用 `cooperation_id`，完整保留为字符串。读取数字 ID 时使用能保留整数精度的解析方式；不得经浮点数转换。相同名称、合同编号或 business_id 的不同协商都要保留。
- 同一 ID 在不同页或人员结果中重复时只保留一条。字段一致则保留首次记录；状态、时间等字段不一致时保留首次记录并明确存在字段冲突，不擅自判定哪条更新。
- 缺少或无法无损读取 cooperation_id 的记录单列为“无法去重的记录”，不按名称猜 ID，不静默丢弃；此时不能宣称合并结果已完整去重。
- 未指定排序时，保留人员输入顺序及各人的返回顺序，并说明按发起人汇总；每次请求的 order 不代表合并结果已具备服务端全局排序。用户指定按发起时间排序时，对已取得的合并结果按 create_time 排序，同值保持原顺序；缺失时间置后并注明。部分结果的排序只适用于已获取记录。
- 展示协商名称、协商 ID、发起人、用户需要的日期、[页面状态与确认人数](response-fields.md)。同名但不同 ID 的记录分别列出。
- 总数使用“已获取并去重 N 条”，不直接相加各人的条数或各页条数。仅当所有目标人员已确认、每人的末页均成功且 ID 均可识别时，才说明本次所有人员已查完；字段冲突另行注明。
- 合并集合没有服务端统一 page_token、has_more 或总数，不拼接或复用任一人的 token，不伪造合并后的 MCP 响应。后续分页保留逐人的上下文；本地分段展示应注明是已获取结果的分段。

## 空结果与失败

- 成功空列表表示该人在共同条件下未命中，不影响其他人的并集；只有所有人成功查完且均为空，才报告本次完整查询无匹配。
- 任一 HTTP/业务 403 立即停止整个流程，包括尚未查询的其他人及后续详情、文件与报告调用，展示接口权限原因；不切换身份、环境或接口。401 按同 profile 的认证流程处理，不继续用未授权上下文查询其他人。
- 其他失败保留已成功获取的记录，注明失败人员和未完成分页；不能当作空结果或输出完整总数。没有自动补查或重试；补查须保留原人员、共同条件及分页上下文。
