## 自动检查的三个层次

| 运行方式 | 检查什么 | 结果边界 |
|---|---|---|
| `ruby tests/validate_contract.rb` | 解析 API YAML 中的业务策略、角色规则、组差异、必需 VERIFY 和 readiness | 不读取 SKILL 文案查找关键词；无真实证据时 `business_runtime=NOT_RUN`。草稿缺口退出 2，不能写成整包通过。 |
| `ruby tests/validate_contract.rb --self-test` | 用刻意构造的正反样例验证检查器能接受正确证据、拒绝错误证据 | 输出 `SYNTHETIC_VERIFIER_SELF_TEST`、`business_runtime=NOT_RUN`；不是产品业务测试，也不是跨 Agent 测试。 |
| `ruby tests/validate_contract.rb --evidence <脱敏JSON路径>` | 核对本次实际确认、请求、前后快照、授权关联及逐资源结果 | 仅给提供的具体场景判定；未提供场景、处理器和平台保持未测试。命令本身不发起网络请求。 |

退出码：`0` 表示本次声明的检查没有错误且契约无未闭合项；`1` 表示契约矛盾或证据不满足断言；`2` 表示仍有诚实记录的开发缺口。即使某组真实业务证据通过，整包仍可能因为影响预检缺口而退出 2。

## 脱敏运行证据格式

指定普通核心test额外声明 `run.scope_mode=ORDINARY_SELECTED_ENTRIES`、`environment=test`、`result_scope=SELECTED_ENTRIES_ONLY`、`all_related_effects_verified=false`。`related_effects` 含 `management=SERVER_MANAGED`、`disclosed=true`、`strict_no_related_changes=false` 及说明来源。确认中的 `related_effects_accepted=true` 来自同一次用户具体确认，不另造授权。

这个模式的 `manifest.affected` 是指定核验入口集合，与 `entries` 同ID；每个 `entry.impact_ids` 只指自身，不声称完整关联展开。写调用 `impact_complete=false`，不得为通过验证伪填true。`entries/affected/before/after` 各资源行都标注 `resource_type=ORDINARY_CONTRACT`、`handler=ORDINARY_CONTRACT`、实际读取的 `assembly_id`（null或字符串0）。一次小批次只提交一次；实际接口请求体不包含这些验收字段。结果只强制本次记录及双角色回读，其他观察另报。下文其余原格式保留；完整影响要求适用于原完整范围模式，不能据此重新拒绝已满足条件的普通核心test。

证据是**实际执行记录的归一化视图**，不是接口请求体或原生响应。采集者从真实工具调用、用户确认、当前响应和快照整理；不允许通过修改合成样例的 `synthetic` 标签制造真实运行记录。检查器不自行鉴定外部采集来源真实性，验收者仍应能沿 `evidence_ref` 回到对应脱敏证据。

顶层为 `version: 1`、`provenance` 和 `runs` 数组。`provenance` 必须提供 `kind: LIVE_CAPTURE`、`synthetic: false`、`environment: test`、`transport: CLI/MCP`、`agent`、`captured_at`、`evidence_ref`。真实业务证据与只读探针报告分开保存，不写 Token、Cookie、Authorization Header 或原始完整敏感响应。ID 可一致脱敏为字符串，但必须保留同一对象及内部员工 ID 类型的对应关系，不用浮点数字传递长整型。

每个 run 的字段如下；具体结构可参考 `tests/self_test.rb` 的合成样例，但合成内容不能作为运行证据。

| 字段 | 采集内容 |
|---|---|
| `id`、`scenario`、`transport`、`requested_action` | 本次执行标识、场景、通道和原始业务动作分类；原始意图不是从最终执行结果倒推。 |
| `recipient` | `employee_id`、`tenant_id`、`id_type: INTERNAL_EMPLOYEE_ID`、有序 `department_ids`；空部门数组必须是实际观察结果。 |
| `operator` | 当前内部员工 ID，以及实际观察的 `personal_handover`、`all_handover` 布尔权限。 |
| `selection` | `mode: EXPLICIT/ALL_RESULTS`、`frozen: true`；全选另含 `pagination_complete: true`、`dynamic_filter_submitted: false`。 |
| `manifest.entries` | 冻结入口的 `resource_id`、可空的 `group_id`、完整 `impact_ids`。 |
| `manifest.affected` | 全部影响资源的 ID 和 `resource_type`。组本体为 `CONTRACT_ASSEMBLY`；子合同为 `ORDINARY_CONTRACT`，但标明 `handler: CONTRACT_ASSEMBLY` 和 `parent_assembly_id`，防止误套普通处理器。 |
| `manifest.exclusions` | 排除资源 ID 和真实原因；不能与最终影响资源重叠。 |
| `manifest.assembly_memberships` | `assembly_id`、完整 `member_resource_ids`、实际 `expected_member_count`、`complete: true`、成员查询的 `evidence_ref`；数量与成员集合必须一致。 |
| `before`、`after` | 逐资源 `resource_id`、`resource_type`、当前 `owner_id`、`submitter_id`、普通/子合同的 `demand_employee_ids`、`evidence_ref`。普通合同及父组另记录可空 `department_id`；组处理器的子合同不要求采集或校验该字段，不用空值补造。验创建来源时另用 `creator_id`，不得代替当前 owner。 |
| `confirmations` | 用户具体确认的本地标识、顺序、入口／影响／排除 ID 集、接收人及 `evidence_ref`；`user_confirmed` 必须来自实际用户确认。 |
| `calls` | 实际调用顺序 `sequence`、`kind: READ/WRITE/VERIFY`、recipe、采集请求标识、HTTP/业务判断；写调用另记录入口、影响、接收人、确认标识、时间、`outcome: CONFIRMED/REJECTED/UNCERTAIN`、未构造管理或身份覆盖标记及提交前快照是否仍一致。VERIFY 记录实际核对的 `resource_ids`。 |
| `batch_reconciliations` | 一个 run 内自动续发后批时必需。每项含上一批 `request_id`、实际核对顺序 `sequence`、来源 `evidence_ref` 与完整 `results`（逐影响资源的 `resource_id/status`）。核对顺序必须晚于该批写入及相应回查、早于下一批写入；结果与最终报告一致，不能有 UNVERIFIED 或缺项。单批没有自动后批时可省略。 |
| `resume` | 明确续办作为新 run 时记录 `previous_run_id`、`user_instruction_ref`、`preflight_evidence_ref`。前次 run 必须一并留存；新影响清单不得包含前次仍为 UNVERIFIED 的资源。具体确认仍由新 run 的 confirmations 绑定，来源可直接使用该次明确续办指令，不要求重复确认。 |
| `records` | 由本次响应或有前后依据的回查关联而成的授权/结果证据，规则见下文。 |
| `results` | 逐影响／排除资源的展示结果，使用契约状态：`VERIFIED_CHANGED`、`NOT_NEW_SUCCESS`、`EXCLUDED`、`FAILED`、`UNVERIFIED`、`NOT_EXECUTED`。 |
| `reported_success_count`、`reported_all_success` | Agent 实际报告的确证变化数量与整批结论，不能从入口条数推算。 |

`records.request_id`、`records.execution_id` 以及 `records.status` **不是声称后端 Authorization 原生具有这些字段**。它们由采集者关联“本次哪一次请求的哪一段响应／快照”得到：`request_id` 对应采集的调用标识，`execution_id` 对应 run ID；若另有服务端 trace/request ID，单独保留该真实字段，不能为缺失字段编造服务端值。`status` 是证据判定映射，不是复制 HTTP `success` 或假设后端逐项成功。

`calls.sequence`、确认及批次核对的 `sequence` 均是同一实际采集时间线上的顺序编号。后批必须在上一批逐资源核对完成后发送；不能用全流程结束后的统一回查补造“当时已核对”。拒绝或不确定的写响应会终止本次自动执行，即使稍后已查清，也需明确续办建立新的执行记录。

每条记录必须有 `resource_id`、`receiver_employee_id`、`evidence_ref` 和 `attribution`。确证变更可用：

- `AUTHORIZATION_IN_CURRENT_RESPONSE`：本次响应中实际返回该资源的授权，配合对应前后快照核对。
- `NEW_AUTHORIZATION_IN_READBACK`：允许的只读回查发现可归因本次且写前不存在的新授权；同时提供 `authorization_id`、`absent_from_before: true`、`before_evidence_ref`，仍须逐资源核对角色变化。
- 明确失败或跳过：只在有当前执行的明确错误／未执行证据及原因时映射，不能把缺少授权记录直接映射为失败或跳过。没有足够事实时使用 `UNVERIFIED`。

合同组可以只有一条父组授权。完整成员证据和逐成员角色／需求人回查齐备时，该父组授权可支持其成员的核对；每个成员不需要虚构独立 Authorization。子合同部门缺失、为空或与预期不同均不参与 Skill 交接结果判定，也不触发额外详情查询；后端部门联动行为不由这项 Skill 验收。普通合同与组子合同的角色断言必须选择各自处理器。

检查器支持的场景标识为 `INITIAL_OWNER`、`CURRENT_OWNER_DIFFERS_CREATOR`、`ORDINARY_EQUAL_ROLES`、`ORDINARY_DIFFERENT_ROLES`、`SUBMITTER_ONLY`、`PERMISSION_DENIED`、`THIRD_PARTY`、`SERVER_REJECT_AFTER_PRECHECK`、`MIXED_RESULTS`、`EMPTY_RECORDS`、`HISTORICAL_RECORD`、`TIMEOUT_STOP`、`PREEXISTING_TARGET_OWNER`、`FROZEN_ALL_RESULTS`、`SERIAL_GROUP_BATCHES`、`ASSEMBLY_OWNER_ONLY`、`ASSEMBLY_SUBMITTER_ONLY`、`ASSEMBLY_BOTH_ROLES`。一个标识只代表所提供的实际分支，不代表整行多种条件已全部覆盖。`INITIAL_OWNER` 用 `observations` 保存创建路径及其来源证据，不在交接测试器中执行创建。
